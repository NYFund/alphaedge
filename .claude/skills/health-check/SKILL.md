# AlphaEdge 健檢

**本檔是健檢規範的唯一來源。** 要調整檢查範圍、清單或門檻，改本檔，不要在 prompt 裡臨時改口徑——
口徑一變，前後兩次健檢的結果就無法比較。

## 0. 為什麼要有這份規範

「找問題」本身沒有終點：高嚴重度的修完，就會輪到命名、措辭、可讀性，永遠找得到。
健檢要能收斂，靠的是三件事，本檔逐一寫死：

1. **範圍依觸發時機分層**——平常只審 diff，全專案只在里程碑。
2. **嚴重度門檻**——只有正確性問題當場修，其餘進 backlog，「零發現」不是目標。
3. **同類問題出現第二次就改成機器檢查**——讓下一輪健檢不必再找它，健檢會越做越薄。

## 1. 三層檢查與觸發時機

| 層級 | 何時 | 範圍 | 通過條件 |
|------|------|------|----------|
| 自動檢查 | 每次 commit | 第 2 節的指令 | 全綠 |
| `diff` 健檢 | 每完成一段工作 | 本次 diff ＋ 直接呼叫端 ＋ 對應測試 | 本次改動無 P0／P1 |
| `milestone` 健檢 | 里程碑才做 | 全專案，依第 4 節清單 | 全專案無 P0／P1 |

**做完一段工作不做全專案健檢。** 使用者沒明講 `milestone` 就一律走 `diff`。

## 2. 自動檢查（兩種模式都先跑）

與 CI 同口徑，任何一項紅就先修，不進入人工審查：

```bash
uv run ruff check . && uv run ruff format --check .
uv run python scripts/check_layer_deps.py
uv run python scripts/check_doc_paths.py
uv run python scripts/check_api_orphan_methods.py
git add -A && uvx pre-commit run --all-files   # 必須在 git add 之後，否則新檔漏掃
uv run pytest -m "not slow" -rs
```

動到 `core/backtest/`、`core/execution/`、`core/portfolio/`、成本模型或策略時，加跑
`./scripts/run_regression.sh`（回歸雙線）。

**已經由上面這些工具管住的東西，人工審查一律不報**：格式、import 排序、未使用 import、
裸 `except`、`exc_info=`、註解引用 backlog 編號、文件路徑失效、分層違規。

## 3. `diff` 模式

1. 取範圍：`git diff main...HEAD` 加上未 commit 的變更。
2. 對每個變更的函式／類別，找出**直接呼叫端**與**對應測試**，一併納入。不往外擴第二層。
3. 依第 4 節清單審查，但只看這個範圍。
4. 範圍外順手看到的問題：**不修、不展開**，P0／P1 在回報中列一行，其餘忽略。

## 4. 檢查清單（依風險排序）

這份清單來自 2026-09-25 的全專案健檢——那次發現的問題幾乎全落在前四類，
而不是「死碼」或「風格」。

### A. Money path 正確性（最高優先）

範圍：`core/live/`、`core/broker/`、`core/dao/`、`core/execution/`、`core/portfolio/`、
`core/backtest/models/`（成本）。

- 會算錯金額、下錯方向／數量／價格、重複送單或漏送單。
- 回測與實盤的語意分岔：同一條規則在兩邊的實作不同（風控截斷、成本公式、時段、停損順序）。
- 例外被吞掉變成「無資料」或靜默略過——應該響的沒響。
- 風控／守門擋單時沒有寫 `live_risk_event`，導致 parity 歸類不到。

### B. 有定義、無執行端

- 設定欄位、檢查方法、類別已經寫好，也被文件或註解寫成保證，但**全庫零呼叫**。
- 判準：`grep` 該名稱，除了定義與測試之外沒有呼叫端 → 發現。
- 比死碼危險：死碼只是沒人用，這一類會讓人以為問題已經被擋住。

### C. 假綠燈

- 測試自己設定、自己斷言（同義反覆）。
- 指令失敗、掃描結果為空時仍然通過（`set() <= x` 恆真、`returncode` 沒檢查）。
- 護欄範圍漏掉某些目錄。
- **驗證方式**：刻意破壞被測行為，確認測試會紅。沒做這一步不算確認。

### D. 重複實作已分岔

- 同一條規則寫在多處，且語意已經不同（fallback 不同、邊界不同、常數寫死不同值）。
- 刻意重複且**有書面理由**的不算發現（兩邊 docstring 互指並寫明差異即可）。

### E. 照著文件做會出錯（只在 `milestone` 全面掃）

- README、`docs/`、`strategy_lab/` 的範例跑不動、欄名／檔名／類別名錯誤。
- 判準是「照抄會出錯」，不是「措辭可以更好」。

### F. 不列入

- 風格、命名、措辭、「可以更好」的重構建議——除非它直接造成 A～E 的問題。
- 覆蓋率數字本身。
- 前次健檢已記錄為**乾淨**的項目（見 `backlog/重構後全專案健檢.md` 末的「確認乾淨的部分」），
  除非本次 diff 動到它。
- 已在 backlog 追蹤中的問題：引用它，不要重報。

## 5. 嚴重度與處理方式

| 等級 | 定義 | 處理 |
|------|------|------|
| P0 | 會造成實際損失或錯單；實盤路徑上的錯誤行為 | 當場修，修完再繼續其他工作 |
| P1 | 假綠燈、無執行端的防線、回測結果錯誤 | 當場修（`diff` 模式）；`milestone` 模式列入 backlog 並排最前 |
| P2 | 潛伏錯誤（目前無呼叫端觸發）、照著文件做會出錯 | 寫進 backlog，不當場修 |
| P3 | 其他 | 不報 |

- **改 money path 行為的修正**（即使是 P0／P1）若正逢實盤演練期間，先回報使用者，不自行動手。
- 寫進 backlog 前先載入 `manage-backlog` skill。

## 6. 輸出格式

每個發現一條，依嚴重度排序：

```
[P1] core/live/risk/risk_manager.py:123 — 一句話描述缺陷
  失敗情境：具體輸入／狀態 → 錯誤結果
  確認方式：grep 結果／刻意破壞後測試轉紅／實際執行輸出
  處理：當場修 ／ 寫入 backlog（哪份文件） ／ 已在 backlog（哪份文件的哪一步）
  [機器化] 同類問題第二次出現——建議改成 pre-commit／測試／check_*.py
```

- **沒有確認方式的一律不報**：「看起來可能有問題」不算發現，要先 grep 或實跑確認。
- 最後一行給結論：`通過`（無 P0／P1）或 `不通過`（列出 P0／P1 編號）。
- 零發現就直接寫「通過，無 P0／P1」，不要為了有東西可報而降級去找 P3。

## 7. 收尾：把重複出現的問題機器化

每次健檢結束時檢查：本次的發現裡，有沒有哪一類**過去已經出現過**？
有的話，提議對應的機器檢查（pre-commit hook、`tests/test_*` 護欄、`scripts/check_*.py`），
讓它從人工清單移到第 2 節的自動檢查。本檔第 4 節的清單應該隨時間**變短**，不是變長。
