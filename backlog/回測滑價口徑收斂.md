# 回測滑價口徑收斂

## Abstract

- **背景／問題**：2026-09-17 全專案盤點滑價路徑，找到四項缺口。共同特徵是**錯了不會報錯**，只會讓成本靜默偏低：
  1. **期貨的強制出場與換月轉倉完全不經過 `FillModel`**。健檢第五輪收斂的 Phase1-8 第 2 項原本同時列了台股與期貨兩處，**只做完台股那一半**（該份 backlog 已於 2026-09-17 結案移出，內容見 git 歷史 `148cae9`）。`TwFuturesSettlementModel` 至今沒有 `fill_model` 參數。
  2. **期貨跳動點寫死 1 點**。`factory.py:185` 固定用 `TwFuturesSpec()`，但滑價是以跳動點表達的，TE／ZEF／TF／ZFF 的跳動點不是 1 點；而且一次回測只有一個 spec，策略的 `products` 卻可以有多個商品。
  3. **做多開倉餘額不足時靜默丟棄**。`StockPositionManager.open_position():110` 的餘額檢查不成立時直接回傳 `None`，**沒有 log、沒有事件計數**，`Backtester.execute_open_signal():542` 也只是不收集。開了滑價之後成交價高於 sizer 估算的參考價，這條路徑正好會被觸發。放空路徑（`:200`）與期貨（`futures/position_manager.py:365`）都有警告，只有做多這條沒有。
  4. **`clamp_filled_price()` 就地修改訂單**。`fill_model.py:476` 直接 `order.price = clamped`，與 `fill()` docstring 明寫的「絕不就地修改傳入的 order」相反。今天沒出事是因為 `validate()` 先擋掉了區間外的單，夾價只會發生在滑價產生的副本上——這是靠呼叫順序保住的，不是靠設計。
  5. **強制出場的滑價後價格不做任何區間檢查**。`apply_fill_price()`（`settlement_model.py:829`）只換價格就回傳：策略自己送的平倉單超出當日 `[low, high]` 時至少會警告並計入 `close_price_out_of_range`（`backtester.py:355`），強制出場這條完全沒有。當沖日終以收盤價回補、再加滑價，價格就可能落在當日沒出現過的位置，而且無聲無息。**期貨在 S3 接上滑價之後會繼承同一個問題**。
  6. **期貨策略誤用基底 `FillConfig` 會靜默退成基點模式**。`TwFuturesFillModel.get_slippage_ticks()`（`fill_model.py:837`）以 `isinstance(self.config, FuturesFillConfig)` 判斷，不是就回 0，改走 bps；`factory.py:191` 的 `strategy.fill_config or FuturesFillConfig()` 也不檢查型別。`BaseFuturesStrategy.fill_config` 只有型別標註擋不住這件事——寫成 `FillConfig(slippage_bps_buy=...)` 一樣跑得完，只是假設默默換了一種。
- **目標**：
  - 不論是策略自己送的單、引擎強制出場的單、還是換月轉倉的兩腿，台股與期貨都吃同一組滑價設定。
  - 跳動點逐商品查表，`slippage_ticks_*` 在每個已登錄商品上換算正確。
  - 因滑價而開不進去的單，在報表上看得見。
- **範圍界線（不做）**：
  - **不改台股強制出場**：三條路徑已經走 `apply_fill_price()`，本文件只跟著它的口徑走。
  - **不改逐日盯市**：`mark_position()`／`settle_daily()` 是評價不是成交，不套滑價。
  - **不新增滑價旋鈕**：強制出場沿用策略既有的 `fill_config`，不另外開「強制出場專用滑價」。
  - **不動成交量上限與券源檢核**：強制出場只補「拿不到理想價」，拒單或縮量會讓部位違規留倉。
  - **不改 `EqualWeightSizer` 的公式**（見 D3）。
  - **不登錄未查證的商品跳動點**：查不到就維持現狀，不猜。
- **驗收標準**：
  1. 期貨策略設了 `slippage_ticks_*` 之後，三條強制出場路徑與轉倉兩腿的成交價都含滑價，各有一條測試。
  2. 已登錄商品在 `slippage_ticks=1` 下的價差等於該商品的一個跳動點；未登錄商品查表時中斷。
  3. 做多開倉因餘額不足被擋時，log 與事件計數都看得到，且該計數出現在事件報表。
  4. `clamp_filled_price()` 回傳副本，傳入的訂單物件不被改動，有測試釘住。
  5. 強制出場的成交價超出當日區間時會警告並計數，台股與期貨同一個口徑。
  6. 期貨策略給了基底 `FillConfig` 時當場中斷，不會靜默改用基點。
  7. `./scripts/run_regression.sh` 雙線**零變動**；`pytest` 全數通過且條數不減；`python scripts/check_layer_deps.py` 通過。

### 滑價在哪些路徑生效

| 路徑 | 台股 | 期貨 |

| 策略開倉單（`execute_open_signal()`） | ✅ | ✅ |

實際套用的位置：

- 台股：`settlement_model.py:500`（`force_cover_position()`，當沖日終／追繳／持有天數／停券共用）與 `:825`（`force_exit_long_position()`，做多無報價出場），兩處都經 `apply_fill_price()`（`:829`），`fill_model` 由 `factory.py:116` 注入。

### 跳動點

```python
# core/backtest/models/instrument_spec.py:231 起
class TwFuturesSpec(InstrumentSpec):
    DEFAULT_TICK_SIZE: float = 1.0  # 台指期系列的最小跳動點（點）

    def __init__(self, tick_size: float = DEFAULT_TICK_SIZE) -> None:
```

`TwFuturesFillModel.apply_tick_slippage()`（`fill_model.py:844`）以 `getattr(self.instrument, "tick_size", …)` 取值，而 `factory.py:185` 建的是不帶參數的 `TwFuturesSpec()`。**一次回測只有一個 spec、只有一個跳動點**，但策略的 `products` 可以有多個商品——這是 `to_units()` 早就遇過的同一類問題（乘數逐契約不同，所以改由 `FuturesPosition.multiplier` 提供）。`README.md:111` 已經記下這件事，但只是註記，沒有修。

### 各策略目前的設定

| 策略 | 滑價 | 量能上限 |
|------|------|----------|
| `ForeignSellShortDayTradeStrategy` | 雙邊 10 bps（`SLIPPAGE_BPS`） | 當日成交量 5% |
| `MomentumStrategy1` | 未設定 → 0 | 無 |
| `MomentumFuturesStrategy` | 未設定 → 0 | 無 |

三支之中只有一支開了滑價，而且是台股。**期貨側的缺口目前是零影響**——這也是為什麼它可以在不重產任何 baseline 的情況下先補起來。

### 盤點時確認沒問題的項目

以下逐一查過，行為與文件一致，本文件不動它們：

- 開倉腿滑價後超出當日區間會夾回並計入 `fill_price_clamped`；平倉腿只警告、計入 `close_price_out_of_range` 不拒單（拒掉平倉會讓部位被迫留倉）。
- 手續費、證交稅、期交稅一律以**含滑價的成交價**計算。
- 期貨的跳動點優先於基點，兩者都設時以跳動點為準。
- 滑價方向寫死（買進往上、賣出往下），呼叫端不能傳負值讓績效變好。
- 對齊檔位取對下單者不利的一側。
- 低於半個檔位的 bps 會被檔位吸收（`core/backtest/README.md` 已載明）。
- 成交量上限只在日 K 生效，tick 級未實作（同上已載明）。
- 檔位表 `PRICE_TICK_TABLE` 是**普通股**的升降單位，ETF 的規則不同；日 K 路徑在 `StockQuoteAdapter` 以 `filter_common_stocks()` 濾掉 ETF 與權證（只留 4 碼、1001~9958），所以現在不會套錯。**但 tick 路徑沒有這道過濾**——日後 tick 庫若含 ETF，滑價對齊檔位就會失真。目前 tick 資料源正在搬家（見 [台股tick改用TimescaleDB.md](台股tick改用TimescaleDB.md)），等該份完成、真的有 ETF tick 時再處理，本文件不做。

## 步驟詳述

### S1. 待裁示事項定案 ✅

- **目的**：D1~D6 決定要改幾個呼叫點與計數名稱，先定案避免返工。
- **做法**：逐項在〈待裁示事項〉表填入裁示與日期；偏離建議時同步修改對應步驟的做法。
- **產出**：本文件。
- **驗證方式**：表內沒有「待定」。
- **相依**：無。
- **完成（2026-09-17）**：六項全數採建議（D5、D6 為複查後新增）——D1 到期出場要套滑價、D2 轉倉兩腿都套、D3 `EqualWeightSizer` 公式不動（只做 S6 的可見度）、D4 事件計數命名 `rejected_insufficient_balance`、D5 強制出場超區間只警告不夾回、D6 期貨 `fill_config` 型別不符拋 `TypeError`。沒有偏離建議，S2~S10 的做法原樣執行。

### S2. `apply_fill_price()` 上移到基底 ⬜

- **目的**：兩個 `SettlementModel` 各寫一份「套滑價」必然漂移，台股那一半已經示範過寫法，期貨不要再抄一次。
- **做法**：
  - 把 `TwStockSettlementModel.apply_fill_price()` 上移到 `BaseSettlementModel`，型別由 `StockOrder` 改成 `BaseOrder`（`copy.copy()` 對兩種訂單都成立）。
  - `BaseSettlementModel.__init__` 收 `fill_model: Optional[BaseFillModel] = None`；台股子類別改為透傳。
  - **保持「只取成交價、不走 `fill()`」**：`fill()` 會做券源檢核與成交量上限，強制出場被拒或被縮量等於讓部位違規留倉。這個理由要留在基底的 docstring 裡。
- **產出**：`core/backtest/models/settlement_model.py`、`tests/backtest/test_settlement_fill_price.py`。
- **驗證方式**：台股既有測試全過；新增基底方法的單元測試（無 `fill_model` 時原物件回傳、有滑價時回傳副本且不改動原訂單）。
- **相依**：無。

### S3. 期貨強制出場套滑價 ⬜

- **目的**：追繳平倉與到期出場吃到和策略同一組滑價。
- **做法**：
  - `TwFuturesSettlementModel.__init__` 加 `fill_model: Optional[BaseFillModel] = None`，`build_tw_futures_backtester()` 注入與引擎同一個 `TwFuturesFillModel`（台股那邊是同一個寫法）。
  - `close_position_at()` 改成 `self.position_manager.close_position(self.apply_fill_price(order))`。
  - 兩個呼叫點（追繳 `:1185`、到期 `:1388`）不用改，改一處即可覆蓋；D1 若裁示到期出場不套滑價，才需要拆成兩條路徑。
- **產出**：`core/backtest/models/settlement_model.py`、`core/backtest/factory.py`。
- **驗證方式**：
  - 新增測試：`FuturesFillConfig(slippage_ticks_buy=1, slippage_ticks_sell=1)` 下，追繳平倉的成交價比結算價差一個跳動點，方向對持有者不利（多單賣出往下、空單回補往上）。
  - 到期出場同樣一條。
  - `./scripts/run_regression.sh` 零變動。
- **相依**：S2、D1。

### S4. 換月轉倉兩腿套滑價 ⬜

- **目的**：轉倉成本不再只算一半。
- **做法**：
  - `roll_single_position()`（`:1292`）的平倉腿由 S3 的 `close_position_at()` 自動涵蓋。
  - 開新月那一腿目前直接 `position_manager.open_position(FuturesOrder(...))`，改成先過 `apply_fill_price()`（D2 裁示要做時）。
  - log 印的 `@ {entry_price}` 要改成印**含滑價後**的價格，否則 log 與實際入帳價不一致。
- **產出**：`core/backtest/models/settlement_model.py`。
- **驗證方式**：轉倉測試：多單轉倉時，舊月賣出價往下一檔、新月買進價往上一檔；`account.trade_records` 的轉倉筆數不變。
- **相依**：S3、D2。

### S5. 逐商品跳動點查表 ⬜

- **目的**：`slippage_ticks_*` 在每個商品上都換算成正確的點數。
- **做法**：
  - `core/utils/constant.py` 新增 `FUTURES_TICK_SIZE: dict`，比照 `FUTURES_MULTIPLIER` 的規矩：
    - **只登錄已查證的商品**，查表一律 `FUTURES_TICK_SIZE[code]`，**不要 `.get(code, 預設值)`**——猜錯不會有徵兆，只會讓滑價靜默偏掉。
    - 查證來源與日期寫進註解。跳動點曾經變更過的商品，比照 `PRICE_LIMIT_RATIO` ／ `_LEGACY` ／ `_WIDENED_DATE` 改成帶生效日的表達方式，不可用單一數值。
  - `TwFuturesFillModel.apply_tick_slippage()` 改為依 `order.product` 查表，查不到時**沿用 `instrument.tick_size`**（維持現行行為），並在 log 記一次警告；`TwFuturesSpec.DEFAULT_TICK_SIZE` 保留給沒有商品資訊的呼叫端。
  - `round_to_tick()` 同樣受影響：對齊檔位要用該商品的跳動點，否則滑價算對了、對齊又把它推回去。
- **產出**：`core/utils/constant.py`、`core/backtest/models/instrument_spec.py`、`core/backtest/models/fill_model.py`、`core/backtest/factory.py`。
- **驗證方式**：
  - 參數化測試：每個已登錄商品在 `slippage_ticks=1` 下的價差等於該商品一個跳動點。
  - 未登錄商品查表時 `KeyError`（測試釘住這個行為是刻意的）。
  - `tests/test_futures_cost.py` 既有的 `tick_size=0.05` 案例不受影響。
- **相依**：無（可與 S3 並行，但兩者都動 `fill_model.py`，建議 S3 先進）。

### S6. 做多開倉餘額不足改為可見 ⬜

- **目的**：讓「滑價把最後一檔推出預算」這件事在報表上看得到。現在它完全無聲：`open_position()` 回傳 `None`，引擎 `if open_position:` 不成立就跳過，沒有 log、沒有計數，回測結果只是少一筆交易。
- **做法**：
  - `StockPositionManager.open_position():110` 的餘額檢查加 `else` 分支：`logger.warning` 印出標的、需要金額（部位價值 ＋ 開倉成本）與可用餘額，格式對齊放空那條（`:200-203`）。
  - 事件計數 `rejected_insufficient_balance`（D4）：計數器由 factory 建立、引擎與各 model 共用同一個 dict，`new_event_counts()` 新增這個 key，`core/backtest/README.md` 的事件對照表補一列。
  - **判斷邏輯完全不動**：開不成還是開不成，只是變得看得見。
- **產出**：`core/managers/stock/position_manager.py`、`core/backtest/backtester.py`、`core/backtest/README.md`。
- **驗證方式**：
  - 新增測試：餘額剛好差一元時回傳 `None`、計數 +1、log 有訊息。
  - `./scripts/run_regression.sh` 零變動（只加 log 與計數）。事件報表是 `Event`／`Count` 長格式（`report/reporter.py:272` 逐鍵輸出），新增 key 只會多一列，不影響既有欄位。
- **相依**：D3、D4。

### S7. `clamp_filled_price()` 改回傳副本 ⬜

- **目的**：`fill()` 的 docstring 明寫「絕不就地修改傳入的 order」，理由是策略可能持有同一個物件、就地改動會讓策略下一根 bar 看到被引擎改過的價量。但 `clamp_filled_price()`（`fill_model.py:476`）直接改 `order.price`。
- **做法**：
  - 改成 `copy.copy(order)` 後改副本再回傳，與 `fill()` 同一種寫法。
  - 在 docstring 註明：目前夾價只會發生在 `fill()` 產生的副本上（因為 `validate()` 先擋掉區間外的單），但那是呼叫順序的巧合，不該當成保證。
- **產出**：`core/backtest/models/fill_model.py`、`tests/backtest/test_fill_model.py`。
- **驗證方式**：新增測試：傳入訂單被夾價後，原物件的 `price` 不變。既有夾價測試全過、`fill_price_clamped` 計數不變。
- **相依**：無。

### S9. 強制出場的成交價做區間檢查 ⬜

- **目的**：讓「滑價把強制出場價推出當日區間」這件事跟策略平倉腿一樣看得見。現在 `apply_fill_price()` 只換價格就回傳，沒有任何檢查。
- **做法**：
  - `apply_fill_price()` 換完價格後，呼叫 `fill_model.warn_close_price_out_of_range(filled_order, quote)`——與策略平倉腿走同一個方法，警告文字與計數 key（`close_price_out_of_range`）都不另外做一份。
  - 因此 `apply_fill_price()` 要多收一個 `quote`。強制出場的呼叫端手上都有當根 bar 的報價或 `quote_map`，唯一的例外是期貨「到期無報價」那條（本來就沒有報價）——該路徑傳 `None`，方法內遇到 `None` 就跳過檢查。
  - **不夾回**（D5）：理由與策略平倉腿一致，寫進 docstring。
- **產出**：`core/backtest/models/settlement_model.py`、`tests/backtest/test_settlement_fill_price.py`。
- **驗證方式**：
  - 新增測試：當沖日終以收盤價回補、滑價把價格推到當日 `high` 之上時，`close_price_out_of_range` +1，且成交價維持含滑價的值（沒有被夾回）。
  - 無報價的期貨到期出場不會因為 `quote=None` 而出錯。
  - `./scripts/run_regression.sh` 零變動（現行唯一有滑價的策略是台股，其強制回補價是否會超出區間由測試覆蓋；若回歸出現差異，代表本來就有超出區間的成交，屬實錯，要先回報再處理）。
- **相依**：S2、S3、D5。

### S10. 期貨 `fill_config` 型別不符時中斷 ⬜

- **目的**：期貨策略寫成 `FillConfig(slippage_bps_buy=10)` 時，`get_slippage_ticks()` 會回 0、改走基點，跑得完但假設換了一種，沒有任何徵兆。
- **做法**：
  - `build_tw_futures_backtester()` 在取用 `strategy.fill_config` 前檢查型別，不是 `FuturesFillConfig` 就拋 `TypeError`，訊息要指出「期貨的滑價以跳動點表達，請改用 `FuturesFillConfig`」（D6）。
  - `BaseFuturesStrategy.fill_config` 的註解補一句：型別標註不是護欄，真正擋住的是 factory 的檢查。
  - **不自動轉型**：把 `FillConfig` 包成 `FuturesFillConfig` 會讓 bps 設定繼續生效，等於默默接受一個本來就不該用在期貨的單位。
- **產出**：`core/backtest/factory.py`、`core/strategies/futures/base.py`、`tests/test_futures_cost.py`。
- **驗證方式**：新增測試：期貨策略帶基底 `FillConfig` 時 `build_tw_futures_backtester()` 拋 `TypeError`；帶 `FuturesFillConfig` 或 `None` 時正常。
- **相依**：D6。

## 後續優化候選（本文件不做）

以下五項是盤點時想到的強化方向，**都不是缺口**——現行行為與文件一致，只是可以更接近真實成交。
每一項都會改變既有回測結果或牽動其他文件，故不納入本文件，等有需求再各自立項。

| 編號 | 優化 | 為什麼值得做 | 代價與前置 |
|------|------|--------------|------------|
| O1 | 台股滑價支援**逐標的**設定 | 期貨已經有 `slippage_ticks_by_product`，台股只有全域 bps。流動性差的中小型股與台積電用同一個數字，等於系統性低估前者的成本 | 會改變所有有滑價的策略結果；需要先有「用什麼決定各標的滑價」的依據（成交量、價差），否則只是換一組拍腦袋的數字 |
| O2 | tick 級改用 **bid/ask** 成交 | 現在 tick 級也是「成交價 ± bps」，但 `TickQuote` 本來就帶 `bid_price`／`ask_price`，買進吃賣價、賣出吃買價才是真實的成本，不需要猜係數 | 相依 tick 資料源（見 [台股tick改用TimescaleDB.md](台股tick改用TimescaleDB.md)）；且 tick 級目前沒有任何策略在用 |
| O3 | 依下單量放大的**市場衝擊**模型 | 現行滑價是固定比例，與下單量無關：買 1 張與買 500 張吃到同一個價。現在只有 `max_volume_share` 這個硬上限（超過就縮量或拒單），中間沒有連續的成本曲線 | 需要 tick 或委託簿資料校準，否則參數同樣是猜的 |
| O4 | 報表輸出**滑價成本統計** | 現在只知道「有沒有開滑價」，不知道它總共吃掉多少。輸出「滑價造成的價差總額／佔總損益比例」才能判斷假設的影響有多大 | 動到 reporter，建議與 [回測績效指標統一由報表輸出.md](回測績效指標統一由報表輸出.md) 同批施作，避免報表改兩次 |
| O5 | 用**實盤成交**回填校正滑價假設 | 最可靠的滑價來源不是猜，是自己的成交紀錄。[實盤下單架構規劃.md](實盤下單架構規劃.md) 的 Phase4-6 已經規劃「比對委託價與實際成交價、計算實際滑價並記錄」，那份資料正好可以回頭定 `SLIPPAGE_BPS` | 相依實盤模組跑出足夠樣本；樣本不足時校準出來的數字比預設值更危險 |

## 為什麼現在改不會動到回測結果

- 回歸雙線都是**台股**：LONG 線是 `MomentumStrategy1`、SHORT 線是腳本情境，兩條都不經過期貨結算模型（S2~S5）。
- 現行唯一的期貨策略 `MomentumFuturesStrategy` 沒有設 `fill_config`，滑價為 0，`apply_fill_price()` 會原物件回傳。
- S6 只加 log 與計數，S7 只改物件複製方式，S9 只加警告與計數（不夾回），四者都不改判斷。
- S10 是防呆：現行三支策略都沒有把基底 `FillConfig` 給期貨策略，拋錯不會弄壞任何既有回測。
- 所以整份是**先補齊、之後才會用到**的修正。反過來做（等用到再修）會讓第一份期貨回測的成本結構就是錯的，而且錯得沒有徵兆。
