# 回測與實盤入口拆分及架構收斂

## Abstract

- **背景／問題**：`run.py` 以 `--mode backtest|live` 同時當回測與實盤的入口，但兩條路徑共用的只有 `--strategy`，而且連它的語意都不同（回測只接一支，實盤接逗號分隔的多支）。全檔 501 行，大約 85% 是實盤邏輯（argparse 定義九個實盤旗標，其中 `--simulation` 與 `--production` 互斥，`_live_only_flags_in_use()` 檢查其餘八個；退出碼 3～7 與 143、SIGTERM 收尾）。共用同一個 parser 已經得靠三處補丁來擋誤用：`_live_only_flags_in_use()` 擋掉回測帶實盤旗標、`docker-compose.yml` 把 `--mode live` 寫死在 `entrypoint`、頂層用 `TYPE_CHECKING` 加延後 import 避免回測也要載入 shioaji。2026-09-25 對照程式碼另外盤點出三個相關的結構問題：
  1. 回測期間與資金寫在策略實例上，CLI 無法覆寫。
  2. 市場規則（成本、商品規格）與策略的成交設定放在 `core/backtest/models/` 底下，共用層與實盤只好反過來 import 回測套件。
  3. 多策略組合只有實盤能跑，回測跑不了。
- **目標**：回測與實盤各自有獨立入口與 parser，改其中一邊的 CLI 不會動到另一邊的檔案；回測期間與資金可以從命令列覆寫；`core/backtest/` 以外的模組不再 import `core.backtest.models`；多策略組合回測留下有數據支撐的去留判斷。
- **範圍界線**：**不做**
  1. 不改 `Backtester` 與 `LiveTrader` 的引擎邏輯；Phase1～Phase3 的回歸雙線都必須零變動。
  2. 不新增實盤旗標，也不改退出碼的數值與語意（排程端依賴這些號碼）。
  3. 不把 `FillConfig` 從策略上移走：成交量上限等設定跟策略風格綁在一起，由策略宣告是合理的，本文件只搬它的定義位置。
  4. Phase4 的多策略組合回測在本文件只做「要不要做」的評估；要做的話另開文件。
  5. 不做 `pyproject.toml` 的 `[project.scripts]` console entry；需要時另議。
- **驗收標準**：
  1. `python -m apps.backtest` 與 `python -m apps.live` 取代 `run.py`，compose、launchd、CI、文件的呼叫端全部改完，`run.py` 刪除。
  2. 回測可用 `--start`／`--end`／`--capital` 覆寫期間與資金。
  3. `core/managers`、`core/strategies`、`core/live` 對 `core.backtest.models` 的 import 歸零，並有分層檢查守住。
  4. 以上每一步都通過回歸雙線（`./scripts/run_regression.sh`）與 `pytest -m "not slow"`。
  5. Phase4-1 留下評估結論。

## Phase1：拆分回測與實盤入口

### Phase1-1. 建立 `apps/` 入口套件與分層登記 ⬜

- **目的**：先把入口放在哪裡、屬於哪一層定下來，後面的步驟才有地方放。
- **做法**：
  - 在專案根目錄新增 `apps/` 套件，裡面**只放入口**（argparse、退出碼翻譯、訊號處理）。
  - **決策：用 `apps/` 而不是 `core/cli/`**。`core` 是函式庫層，不該認識 argparse 與 `sys.exit`，入口必須在 `core/` 之外。它與既有的 `tasks/`（資料維運入口）、`scripts/`（護欄與工具）平行，呼叫方式也沿用 `python -m tasks.update_db` 的慣例。若改用 `cli/` 等其他名稱，只影響這一步與 Phase1-6 的字串替換。
  - `scripts/check_layer_deps.py`：
    - `_LAYER_RULES` 新增 `("apps", 8, "入口層", False)`，與 `run`、`tasks` 同層。
    - **`_SCAN_DIRS` 新增 `"apps"`**：`collect_files()` 只掃 `_SCAN_DIRS` 列出的目錄與 `_SCAN_FILES` 列出的單檔（目前只有 `("run.py",)`），不會自動發現新的頂層套件，不加就整個漏掃。
    - **`_NON_CORE_TOPS` 新增 `"apps"`**：否則 `core/` 反向 import `apps` 不會被判成反向相依。
  - 過渡期 `run` 與 `apps` 兩個登記並存，Phase1-7 刪掉 `run.py` 時一併移除 `run` 的規則、`_SCAN_FILES` 裡的 `run.py` 與 `_NON_CORE_TOPS` 裡的 `"run"`。
  - **映像與安裝**：`core/Dockerfile` 是逐項 `COPY`（`run.py`、`core`、`tasks`），不加的話映像裡沒有 `apps/`；`pyproject.toml` 的 `[tool.setuptools.packages.find]` `include = ["core*", "tasks*", "tests*"]` 也不含它。
    - `core/Dockerfile` 新增 `COPY apps /app/apps`（`ENTRYPOINT` 留到 Phase1-6 再改）。
    - `pyproject.toml` 的 `include` 加 `"apps*"`。
- **產出**：`apps/__init__.py`（模組層級說明字串寫清楚「只放入口、不放業務邏輯」）、`scripts/check_layer_deps.py`、`core/Dockerfile`、`pyproject.toml`。
- **驗證方式**：`python scripts/check_layer_deps.py` 通過；在 `apps/` 放一個暫時的 import 確認它有被掃到，驗完移除；`docker build -f core/Dockerfile .` 後映像內有 `/app/apps`。
- **相依**：無。

### Phase1-2. 拆出回測入口 `apps/backtest.py` ⬜

- **目的**：回測有自己的 parser，只認得回測的旗標。
- **做法**：
  - 把 `run.py` 裡 `main()` 的回測分支搬到 `apps/backtest.py`，參數只有 `--strategy`（單支）與 `--show`／`--no-show`。
  - 策略找不到時沿用現行行為：訊息寫 stderr、列出可用策略、退出碼 2。這一段兩個入口都要用，抽成 `apps/_common.py` 的私有函式（例如 `_resolve_strategy_or_exit()`）與 `EXIT_USAGE` 常數。
  - **`_live_only_flags_in_use()` 不搬**：回測 parser 不認得實盤旗標，argparse 會自己以退出碼 2 拒絕。原本要防的「帶了 `--production` 卻默默跑一場回測」在結構上已經不可能發生。
- **產出**：`apps/backtest.py`、`apps/_common.py`、`tests/test_backtest_entry.py`（從 `tests/test_run_entry.py` 移植回測相關案例）。
- **驗證方式**：
  - `python -m apps.backtest --strategy MomentumStrategy1` 產出與 `run.py` 逐檔相同。
  - `python -m apps.backtest --strategy X --production` 退出碼為 2。
  - 回歸雙線零變動。
- **相依**：Phase1-1。

### Phase1-3. 拆出實盤入口 `apps/live.py` ⬜

- **目的**：實盤入口獨立成一支檔案，改回測 CLI 不會出現在它的 diff 裡。
- **做法**：
  - 搬移 `run_live()`、`_run_live_phase()`、`_check_resync_arguments()`、`_run_resync()`、`_resolve_live_exit_code()`、`PHASE_TO_TIMING`、`RESYNC_PHASE`、`DEFAULT_BROKER` 與全部 `EXIT_*` 常數，連同 `run.py` 頂部那段退出碼說明註解。
  - 現在實盤是入口唯一的用途，`--phase` 可以改成 `required`，但要保留「帶 `--resync-from-broker` 時不可有 `--phase`」的互斥檢查。建議不改：維持現行的手寫檢查，錯誤訊息比 argparse 的清楚，也就不必重寫測試。
  - 延後 import 與 `TYPE_CHECKING` 可以拿掉，改成頂層 import：這支檔案本來就只給實盤用。
  - 順手把 `_run_live_phase(trader: object, ...)`、`_run_resync(trader: object, ...)` 的型別改成 `LiveTrader`。
  - SIGTERM 處理（`raise_on_sigterm()`）與退出碼 143 維持原樣。
- **產出**：`apps/live.py`、`tests/test_live_entry.py`（從 `tests/test_run_entry.py` 移植實盤案例），並檢查 `tests/live/test_live_factory_and_entry.py`（頂層 `import run as run_module`，另以子行程跑 `run.py`）、`tests/live/test_termination.py`（`test_run_entry_exits_with_143_on_sigterm` 在函式內 `import run as run_module` 呼叫 `run_live()`）裡以子行程或 import 呼叫 `run` 的地方。
- **驗證方式**：
  - 原 `test_run_entry.py` 的實盤案例（resync 組合、stale data、退出碼從不為 0 等）全數移植後通過。
  - `python -m apps.live --strategy X --phase open --broker fake --dry-run` 在模擬環境走完一個段落。
  - 注意 `conftest.py` 記錄過的事故：以子行程跑實盤入口的測試曾用本機 `.env` 的金鑰連線。新測試要沿用現有的隔離機制，不要繞過。
- **相依**：Phase1-1。**施作時機**：避開 `實盤下單架構規劃.md` Phase7-1 演練的排程時段；程式合併後到 Phase1-6 改完 launchd 之前，排程仍走 `run.py`（Phase1-5 會讓它繼續可用）。

### Phase1-4. 策略依名稱載入，不再掃描全部 ⬜

- **目的**：`StrategyLoader.load_strategies()` 會 import `core/strategies/` 底下每一個模組，所以正式環境的實盤行程也會執行研究中策略的 module-level 程式碼。載入器有逐模組的錯誤隔離，不會崩潰，但實盤入口其實只需要指定的那幾支。
- **做法**：
  - `StrategyLoader` 新增依名稱查找的方法（例如 `load(names: List[str]) -> Dict[str, Type[BaseStrategy]]`）。問題在於類別名稱和模組名稱之間沒有對照表，要找到類別仍得掃描。可以二選一：
    1. 掃描時只列出模組名稱、不 import，改由命名慣例（類別名轉 `snake_case`）推出模組名，推不到時才退回全掃；或
    2. 維持全掃描，但實盤入口在掃描後檢查 `broken_modules`，只要有任何模組壞掉就記 warning 並推播。**前提是改介面**：`broken_modules` 目前是 `load_strategies()` 內的區域變數，只拿來記一條 warning，呼叫端拿不到；要改成回傳 `Tuple[Dict[str, Type[BaseStrategy]], List[str]]` 或掛成類別屬性公開出來。
  - 選 1 的命名慣例要先確認。現有三支：`ForeignSellShortDayTradeStrategy` ↔ `foreign_sell_short_day_trade_strategy.py`、`MomentumFuturesStrategy` ↔ `momentum_futures_strategy.py` 符合一般 `PascalCase` → `snake_case`；**`MomentumStrategy1` ↔ `momentum_strategy_1.py` 是反例**，一般轉換會得到 `momentum_strategy1`。要走選 1 只能三擇一：轉換規則加上「數字前切底線」、把檔名改成 `momentum_strategy1.py`（連帶改所有引用），或乾脆選 2。
  - 「找不到策略」時列出全部可用策略的功能要保留，這條路徑可以接受全掃描。
- **產出**：`core/strategies/strategy_loader.py`、`apps/backtest.py`、`apps/live.py`，以及對應測試。
- **驗證方式**：新測試在策略目錄放一個 import 就會拋錯的假模組，確認指定其他策略時它不會被 import（選 1），或會觸發警告（選 2）。
- **相依**：Phase1-2、Phase1-3。

### Phase1-5. `run.py` 改為轉發 shim ⬜

- **目的**：呼叫端約 50 處，不可能一次改完。過渡期間舊指令要能繼續用。
- **做法**：
  - `run.py` 只保留：從 `sys.argv` 抽出 `--mode`（預設 `backtest`），把其餘參數原封不動轉給 `apps.backtest.main()` 或 `apps.live.main()`，並以 loguru 記一條 deprecation 警告，寫明新指令。
  - 退出碼要完整往外傳（不可吞成 0 或 1）：launchd 與 compose 會依它判讀。
  - `tests/test_run_entry.py` 縮減成只驗 shim：轉發正確，退出碼與新入口相同。
- **產出**：`run.py`、`tests/test_run_entry.py`。
- **驗證方式**：`python run.py --mode live --strategy X` 與 `python -m apps.live --strategy X` 的退出碼與 stderr 相同；`python run.py --mode backtest --production` 仍回 2。
- **相依**：Phase1-2、Phase1-3。

## Phase2：回測期間與資金可從命令列覆寫

### Phase2-1. 回測期間與資金改由命令列覆寫 ⬜

- **目的**：目前要換回測區間或初始資金只能改策略程式碼，所以參數掃描、walk-forward 與「同一支策略跑不同區間比較」都做不到。
- **現況**（2026-09-25 查證）：
  - `BaseStrategy.__init__` 定義 `init_capital`、`start_date`、`end_date`（`core/strategies/base.py`），各策略在自己的 `__init__` 覆寫。
  - **策略本身也會讀這兩個日期**：例如 `MomentumStrategy1` 用 `self.start_date`／`self.end_date` 決定預載資料的範圍。回測資料源（`TwStockDataFeed`、`TwFuturesDataFeed`）在 `setup(strategy)` 時從策略複製一份；`Backtester.__init__` 也讀 `strategy.start_date`／`end_date`，`core/backtest/factory.py` 則讀 `strategy.init_capital` 建帳戶、讀兩個日期寫進保證金設定。
  - 因此「把日期從策略身上拿走」不是這一步做得到的事，否則要改每一支策略。
- **做法**：
  - `apps/backtest.py` 新增 `--start`、`--end`（`YYYY-MM-DD`）、`--capital`，三者都選填。
  - 覆寫點放在 `core/backtest/factory.py`：`build_backtester()` 新增選填參數 `overrides: Optional[BacktestOverrides]`（dataclass，三個 `Optional` 欄位），在 `build_backtester()` **最開頭、建立任何元件之前**寫回策略實例的屬性（帳戶、資料源、`Backtester` 都會讀這三個值）。這正是 `make_daily_backtest_runner()` 現在手寫做的事，收斂成單一介面。
  - 日期驗證（`start <= end`、不早於資料起點）放在 factory，入口只負責解析字串。
- **產出**：`apps/backtest.py`、`core/backtest/factory.py`（或 `core/backtest/overrides.py`）、`tests/backtest/test_backtest_overrides.py`。
- **驗證方式**：
  - 不帶任何旗標時回歸雙線零變動。
  - 帶 `--start/--end` 時，`trade_records` 的日期全部落在區間內。
  - `start > end` 時退出碼為 2。
- **相依**：Phase1-2。

### Phase2-2. parity 單日回測改走同一個覆寫介面 ⬜

- **目的**：`core/live/factory.py` 的 `make_daily_backtest_runner()` 目前直接改 `replica.start_date`／`end_date`／`init_capital`，等於第二套覆寫邏輯。
- **做法**：改呼叫 `build_backtester(replica, overrides=BacktestOverrides(start=run_date, end=run_date, capital=blueprint.init_capital), write_artifacts=False)`。
- **產出**：`core/live/factory.py`。
- **驗證方式**：`tests/live/` 中涵蓋 parity runner 的測試通過；比對重構前後同一天的 `submitted_orders` 相同。
- **相依**：Phase2-1。

### Phase2-3. 評估「執行參數」與策略是否要進一步分家 ⬜

- **目的**：策略實例現在同時扛著「交易邏輯」與「這一次怎麼跑」。`live_capital` 的存在就是因為 `init_capital` 身兼回測初始資金與實盤額度兩個角色。這一步評估要不要把執行參數整個移出策略。
- **做法**：盤點並寫下結論即可，不在本步驟實作。
  - 列出所有讀 `self.start_date`／`self.end_date`／`self.init_capital` 的策略與引擎程式。
  - 評估兩個方向：
    - (a) 維持現狀，只保留 Phase2-1 的覆寫介面。
    - (b) 引入 `RunContext` 由引擎注入，策略改讀 `self.context.start_date`，`init_capital`／`live_capital` 改由回測與實盤設定各自提供。
  - (b) 的代價是每一支策略都要改寫，以及 `strategy_lab` 的使用方式。只有在出現具體需求（例如參數掃描框架）時才值得做。
- **產出**：本步驟章節末尾的結論段落。結論是 (b) 的話，另開 backlog 文件。
- **驗證方式**：人工判讀。
- **相依**：Phase2-1。

## Phase4：多策略組合回測

### Phase4-1. 評估是否補多策略組合回測 ⏸

- **目的**：實盤支援多支策略共用帳戶（資金額度分配、同標的仲裁、帳戶層風控降級），但 `build_backtester(strategy)` 只接受單一策略，所以實盤實際跑的組合無法先回測，parity 也只能逐策略比對。`實盤下單架構規劃.md`〈多策略〉已經把這點列為已知限制（「帳戶層的組合績效在回測端無法重現」），並約定用 Phase7-1 演練的數據決定要不要補。本步驟就是那個決定點。
- **做法**：
  - 從 Phase7-1 演練紀錄取出 parity 的 `CROSS_STRATEGY_BLOCKED` 與 `CAPITAL_EXHAUSTED` 兩類差異的筆數與金額佔比。
  - 判斷準則（可在評估時修正）：兩類合計佔送單金額的比例夠高，高到「各策略單獨回測績效相加」明顯偏離帳戶實際績效時，就值得做。
  - 若要做：前置條件已具備。跨策略仲裁的判定是 `core/portfolio/aggregation.py` 的純函式，不依賴 broker 與 DB。新文件要處理的是 `Backtester` 如何接多個 sleeve（策略子組合），以及報表如何同時呈現帳戶層與各策略層。
- **產出**：本步驟章節末尾的結論段落；結論是要做的話，另開 `backlog/多策略組合回測.md`，並在 `index.md` 登記。
- **驗證方式**：人工判讀。
- **相依**：**暫緩**，解除條件是 `實盤下單架構規劃.md` Phase7-1 的多日演練完成並留下 parity 分類統計。
