# 回測與實盤入口拆分及架構收斂

## Abstract

- **背景／問題**（2026-09-25 盤點時的狀態）：`run.py` 以 `--mode backtest|live` 同時當回測與實盤的入口，但兩條路徑共用的只有 `--strategy`，而且連它的語意都不同（回測只接一支，實盤接逗號分隔的多支）。全檔 501 行，大約 85% 是實盤邏輯（argparse 定義九個實盤旗標，其中 `--simulation` 與 `--production` 互斥，`_live_only_flags_in_use()` 檢查其餘八個；退出碼 3～7 與 143、SIGTERM 收尾）。共用同一個 parser 已經得靠三處補丁來擋誤用：`_live_only_flags_in_use()` 擋掉回測帶實盤旗標、`docker-compose.yml` 把 `--mode live` 寫死在 `entrypoint`、頂層用 `TYPE_CHECKING` 加延後 import 避免回測也要載入 shioaji。對照程式碼另外盤點出三個相關的結構問題：
  1. 回測期間與資金寫在策略實例上，CLI 無法覆寫。
  2. 市場規則（成本、商品規格）與策略的成交設定放在 `core/backtest/models/` 底下，共用層與實盤只好反過來 import 回測套件。
  3. 多策略組合只有實盤能跑，回測跑不了。
- **現況（2026-10-10）**：`run.py` 已於 2026-10-01 刪除。main 上的入口是 `apps/backtest.py`、`apps/live.py`（共用 `apps/_common.py`）加上 `tasks/` 的三支資料維運入口；
  `feature/post-rehearsal` 已把 `tasks/` 併入 `apps/`（Phase1-8），部署後入口只剩 `apps/` 一個目錄、六支入口。實盤退出碼 3～7 與 143 的數值與語意未變。
- **目標**：回測與實盤各自有獨立入口與 parser，改其中一邊的 CLI 不會動到另一邊的檔案；回測期間與資金可以從命令列覆寫；`core/backtest/` 以外的模組不再 import `core.backtest.models`；多策略組合回測留下有數據支撐的去留判斷。
- **範圍界線**：**不做**
  1. 不改 `Backtester` 與 `LiveTrader` 的引擎邏輯；Phase1～Phase3 的回歸雙線都必須零變動。
  2. 不新增實盤旗標，也不改退出碼的數值與語意（排程端依賴這些號碼）。
  3. 不把 `FillConfig` 從策略上移走：成交量上限等設定跟策略風格綁在一起，由策略宣告是合理的，本文件只搬它的定義位置。
  4. Phase4 的多策略組合回測在本文件只做「要不要做」的評估；要做的話另開文件。
  5. 不做 `pyproject.toml` 的 `[project.scripts]` console entry；需要時另議。
- **驗收標準**：
  1. `python -m apps.backtest` 與 `python -m apps.live` 取代 `run.py`，compose、launchd、CI、文件的呼叫端全部改完，`run.py` 刪除（✅ 2026-10-01）。`tasks/` 的入口也併入 `apps/`，入口只剩一個目錄（🔄 Phase1-8，待演練後部署）。
  2. 回測可用 `--start`／`--end`／`--capital` 覆寫期間與資金（✅）。
  3. `core/position`（2026-10-01 前為 `core/managers`）、`core/strategies`、`core/live` 對 `core.backtest.models` 的 import 歸零，並有分層檢查守住（✅）。
  4. 以上每一步都通過回歸雙線（`./scripts/run_regression.sh`）與 `pytest -m "not slow"`。
  5. Phase4-1 留下評估結論（⏸）。

## Phase1：拆分回測與實盤入口

### Phase1-1. 建立 `apps/` 入口套件與分層登記 ✅

- **目的**：先把入口放在哪裡、屬於哪一層定下來，後面的步驟才有地方放。
- **決策：用 `apps/` 而不是 `core/cli/`**。`core` 是函式庫層，不該認識 argparse 與 `sys.exit`，入口必須在 `core/` 之外；
  `apps/` **只放入口**（argparse、退出碼翻譯、訊號處理），factory 留在 `core`（只組裝，不讀命令列與環境變數做決策）。
- **相依**：無。

> **✅ 完成紀錄（2026-09-30，`7316c8d`）**
> - 新增 `apps/__init__.py`；`scripts/check_layer_deps.py` 的 `_LAYER_RULES` 加 `("apps", 8, "入口層", False)`，`_SCAN_DIRS`、`_NON_CORE_TOPS`、
>   `_DB_DRIVER_GUARDED_DIRS` 加 `apps`；`pyproject.toml` 的 `include` 加 `"apps*"`；Dockerfile 加 `COPY apps`。
> - **超出原規劃**：依 `core目錄邊界收斂.md` 附錄的護欄清單逐一判斷，其餘護欄全數加入 `apps`；
>   **覆蓋率刻意不加**（與入口層一致只量函式庫，理由寫在 `pyproject.toml` 的註解）。
> - 驗證：`check_layer_deps.py` 違規 0；暫時檔確認有掃到；在 `core/utils/__init__.py` 暫加 `from apps import x` 列為違規、結束碼 1。
>   `pytest` 2433 passed。**`docker build` 未在本機驗證**（Docker daemon 未啟動），由 CI 的映像建置與冒煙把關。

### Phase1-4. 策略依名稱載入，不再掃描全部 ✅

- **目的**：舊的 `StrategyLoader.load_strategies()` 會 import 策略目錄底下每一個模組，正式環境的實盤行程也會執行研究中策略的 module-level 程式碼。
- **相依**：Phase1-2、Phase1-3。

> **✅ 完成紀錄（2026-09-30，`d3c715f`）**
> - **偏離原規格：兩個選項都沒採用，改用第三種做法**。`StrategyLoader.load(names)` 先以 AST 讀檔建立「頂層類別名 → 模組」索引（`index_class_modules()`，只解析、不執行），再只 import 命中的模組。
>   - 不走選 1（類別名轉 `snake_case` 推模組名）：`MomentumStrategy1` ↔ `momentum_strategy_1.py` 證明命名慣例不可靠。
>   - 不走選 2（全掃描後檢查壞模組並警告）：研究中策略的 module-level 程式碼仍會在實盤行程裡執行，沒解決問題。
> - 語意：找不到的名稱不出現在回傳值；指定策略所在模組 import 失敗時**直接往外拋**；同名類別出現在兩個模組時拋 `ValueError`；抽象類別視同找不到；語法錯誤的檔案記 error 略過。
>   只有「找不到策略、要列出可用清單」這條失敗路徑才全掃描。
> - 測試：`tests/test_strategy_loader_by_name.py` 7 條。**哨兵模組在拋錯前先寫標記檔**——只斷言「不在 `sys.modules`」的第一版在突變下恆真，改用標記檔後突變會轉紅。
> - 2026-10-10：載入器在 main 上仍是 `core/strategies/strategy_loader.py`；`core目錄邊界收斂.md` Phase2-2 已在 `feature/post-rehearsal` 把它搬到頂層 `strategies/loader.py`，待演練後部署。
