# 實盤委託價格類型設計

## Abstract

- **背景／問題**：2026-10-06 模擬演練第一次送單，`MomentumStrategy1` 的三張買單在券商轉換層失敗——
  委託的 `price_type`（限價／市價）沒有任何程式填寫。`StockOrder`／`FuturesOrder` 的 `price_type` 預設是 `None`，
  原意是「由委託前處理依策略意圖填入」，但這個前處理從未實作；回測不需要這個欄位，所以回測一直正常。
  同日先上了臨時補值（見下方〈現況〉），策略如何表達價格類型的設計**尚未討論**。
- **目標**：決定策略作者怎麼表達一張委託「要成交」還是「照價掛單」，以及實盤怎麼把它換成券商接受的委託，
  讓回測「以收盤價成交」的假設與實盤成交的方式對得上。
- **範圍界線**：只處理實盤委託的價格類型與委託價；不改回測的成交模型；不處理追價、改單（D7 另議）；
  不處理盤中零股與股期（`實盤下單架構規劃.md` Phase6-3、Phase6-4）。
- **驗收標準**：設計經使用者定案；策略產生的委託在實盤都有明確的價格類型與委託價；
  沒宣告或宣告錯誤時在啟動時就擋下，而不是送單時才失敗；臨時補值移除。

> ✅ **S1 已於 2026-10-06 定案**：Q1～Q7 皆有裁示（見各題下方「裁示」）。
> 🔄 **2026-10-06 程式全部完成**（分支 `feature/execution-model`）：S2 只剩「演練中實際送出並取得券商回報」的實測，S3 ✅。見〈S2〉的進度紀錄。

## 設計方向（2026-10-06 討論）

比照業界常見的四層架構（QuantConnect LEAN 的 Algorithm Framework）：

```
Alpha（訊號）→ Portfolio Construction（算量）→ Risk Management（風控）→ Execution（怎麼送）
```

AlphaEdge 已有前三層：`generate_*_signals()` 輸出 `Signal`、`core/portfolio/sizing.py` 算量、`core/live/risk/` 風控。
**`price_type` 沒人填，是因為它屬於還不存在的 Execution 層。**LEAN 的策略完全不碰委託類型，只選一個執行模型；
本設計同樣讓策略只宣告「執行方式」，由新增的執行層依時段與商品換算成券商委託。

**執行層命名（2026-10-06 裁示）**：新增的層使用 Execution 相關命名（對應業界的 Execution Model／EMS）。
注意 `core/broker/` 已有 `shioaji_execution_handler.py`、`execution_dedup.py`，那裡的 execution 指**成交回報**（FIX 的 ExecutionReport），
與本層「決定怎麼送單」語意不同；兩種用法在業界都存在（FIX 也把成交回報叫 ExecutionReport），`core/broker/` 維持原名，實作時在模組說明寫清楚區別。

**目錄與類別（2026-10-06 裁示）**：比照 LEAN 的 Execution Model，策略選 `ExecutionStyle`、由 Execution Model 換算：

```
core/live/execution/
  base.py      BaseExecutionModel
  stock.py     StockExecutionModel
  futures.py   FuturesExecutionModel
```

不採 `core/live/ems/`＋`ExecutionManager`（與 `oms/` 對稱，但 EMS 在業界暗示含拆單、路由、券商連線，範圍比實際大），
也不採 `ExecutionPlanner`（非業界通用詞）。

```
現在：Signal → 算量 → StockOrder(price_type=None) → 風控 → mapper（臨時補值）→ 券商
設計：Signal → 算量 → StockOrder → 風控 → 執行層（依執行方式＋時段填 price_type／委託價／ROD・IOC）
      → mapper（只做機械轉換）→ 券商
```

策略作者只看得到一個設定：

```python
self.live_execution = ExecutionStyle.MARKET  # 要成交；執行層會加保護價，不保證送出的是市價單
```

| 執行方式 | 意思 | 適合 |
|----------|------|------|
| `MARKET`（要成交） | 這筆一定要進出場，價格交給市場決定 | 回測假設「以收盤價成交」的策略 |
| `LIMIT`（照價掛單） | 只接受策略給的價，沒成交就算了 | 掛低接、掛高賣的策略 |

執行層的換算表（策略看不到）：

| 執行方式 ＼ 時段 | 集合競價（`AT_OPEN`／`AT_CLOSE`） | 連續交易（`IMMEDIATE`） |
|------------------|-----------------------------------|--------------------------|
| 要成交（股票） | 買掛漲停、賣掛跌停，`LMT`＋`ROD` | 保護價限價：決策價 ± 幅度、對齊檔位、夾在漲跌停內，`LMT`＋`IOC`（幅度 2%） |
| 要成交（期貨） | 同左（目前沒有段落落在期貨集合競價，見下方說明） | `MKP`＋`IOC`（換月已在用） |
| 照價掛單 | 策略給的價，`LMT`＋`ROD` | 同左 |

集合競價掛漲跌停的理由：集合競價以單一價格撮合，掛漲停只是確保排得進去，成交價仍是競價結果（收盤價），
等同台股版的 MOC（market-on-close），與回測「以收盤價成交」的假設最一致。

**期貨的段落其實都在連續交易時段（2026-10-06 實作時確認，偏離原表的字面）**：上表把 `AT_OPEN`／`AT_CLOSE`
一律視為集合競價，但期貨的段落時窗是 08:45～08:59（日盤 08:45 已開盤）與 13:30～13:44，都不在集合競價。
依同一條原則（連續時段的 `MARKET` 送 `MKP`＋`IOC`），`FuturesExecutionModel` 的兩個段落一律走 `MKP`＋`IOC`，
集合競價那一格的換算保留在骨架裡，段落時窗日後移進 08:30～08:45 開盤前集合競價時才會用到。

## 待討論事項

### Q1. 在哪裡表達價格類型

- 每張委託自己帶（策略或部位建構層建立委託時填 `price_type`）。
- 策略層級逐鉤子宣告（例如比照 `live_schedule`，以 `open`／`close`／`stop_loss` 為鍵）。
- 策略層級一個值，全部委託共用。
- 和其他委託設定（委託條件 ROD／IOC／FOK、滑價容忍、委託張數單位）整合成一組設定。
- 多層並存時的優先順序（委託 > 鉤子 > 策略預設？）。

**裁示（2026-10-06）**：策略層級一個值；**停損固定視為「要成交」**，不受策略宣告影響——出場不該因為價格掛不到而失敗，
這也涵蓋了「被動進場、緊急出場」的常見需求。不做逐鉤子或逐委託的覆寫，等真的有策略需要再加。

### Q2. 意圖的值域

- 只有「限價／市價」兩種，直接對應券商的列舉值？
- 還是用意圖（例如「要成交」「照價掛單」）表達，由實盤依段落與商品換成券商接受的委託？
- 期貨的範圍市價（`MKP`）要不要開放給策略。

**提案（待確認）**：用意圖表達，只有「要成交／照價掛單」兩種（見〈設計方向〉）；券商列舉值與 `MKP` 不開放給策略，只由執行層使用。

**裁示（2026-10-06）**：值命名為 **`MARKET`（要成交）／`LIMIT`（照價掛單）**，採業界最通用的委託語彙（FIX `OrdType`、Zipline、LEAN、Nautilus 皆用）。
不用 `MARKETABLE`：它是監理與券商文件指「價格寬到能立刻成交的限價單」的用語，描述的是換算後的委託形態而非策略意圖。
`MARKET` 是**意圖**，不保證送出的是市價單——比照 CME market order with protection、券商 market-to-limit，執行層會換成帶保護價的限價單；
它與券商列舉 `StockPriceType.MKT` 分屬不同型別，兩者不可混用。
型別名 **`ExecutionStyle`**（先例：Zipline `zipline.finance.execution.ExecutionStyle`，放 `core/utils/constant/live.py`），
策略欄位名 **`live_execution`**（`live_` 前綴沿用 `live_ready`／`live_schedule`／`live_tag`，表示回測不讀）。

### Q3. 「要成交」怎麼換成委託

集合競價以單一價格撮合，掛得比競價價格寬只是確保進得去，成交價仍是競價結果。候選做法：

- 可成交的限價：基準價 ×（1 ± 容許幅度），對齊檔位，夾在漲跌停內（`實盤下單架構規劃.md` D6 原本的建議，容許幅度 2%）。
- 直接掛漲停價（買）／跌停價（賣）。
- 依段落切換：集合競價時段送限價，連續交易時段送市價（期貨要搭配 IOC／FOK）。
- 相關細節：基準價取什麼（策略給的價、快照價、參考價）、容許幅度怎麼定、
  與風控價格偏離上限（`RiskConfig.price_deviation_ratio`，預設 3%）的關係、漲跌停從哪裡取（尾盤段的快照報價沒有漲跌停，要另查合約）。

**裁示（2026-10-06）**：
- 集合競價時段的「要成交」**買單掛漲停、賣單掛跌停**（`LMT`＋`ROD`），不採 ±2%。
  ±2% 在收盤價高於 13:20 快照超過 2% 時會不成交、回測卻會成交；動能股多數離漲停不到 2%，兩者實際差異也不大。
- **風控偏離檢查改比對策略給的決策價**（`Signal.order_price`），防的是策略算錯價；
  執行層產生的保護價只檢查不超出漲跌停。否則漲 2% 的股票掛漲停就偏離 8%，會被預設 3% 的上限擋下
  （`check_price_deviation()`，`core/live/risk/risk_manager.py`）。

**裁示（2026-10-06，補）**：
- 連續交易時段股票 `MARKET` 的保護價採**固定百分比**：決策價 ±2%、對齊檔位、夾在漲跌停內（交易所價格穩定帶的常見定義方式，也是 D6 原本的建議值）。
  不採固定檔數（不同價位實際寬度差很多）與對手價＋N 檔（需即時五檔報價）。目前沒有策略使用 `IMMEDIATE`，規則先定、實作可排在最後。
- 漲跌停取自**券商合約資料**（`contract.limit_up`／`limit_down`，與盤前段同一條路徑）；**取不到就記 warning、略過該檔**，不自行推算。
  新上市前五日無漲跌幅限制的股票會因此被略過。不採交易所公告值（`暫緩工作彙整.md` S6 已暫緩）。

### Q4. 系統自己產生的委託

**裁示（2026-10-06）**：一律視為「要成交」（`MARKET`），由執行層處理、不經策略；換月兩腿的 `MKP`＋`IOC` 正好是連續交易時段期貨「要成交」的換算結果，改由執行層產生。

### Q6. 與回測的一致性

- 回測目前忽略 `price_type`、一律以策略給的價成交；實盤若送限價且掛在快照價，兩邊的成交與否會分歧。
- parity 比對（`實盤下單架構規劃.md` Phase4-8）對「限價沒成交」要怎麼歸類。
- 回測要不要開始讀 `price_type`（例如限價單在 bar 內沒碰到就不成交）——會改變回測結果、須重產 baseline。

**裁示（2026-10-06）**：回測不改。「要成交」正是回測現在的假設；「照價掛單」在回測偏樂觀，
parity 新增「限價未成交」與「收盤鎖漲停排不到」類別量化差異，等累積數據再決定回測要不要讀執行方式。

- **目的**：讓策略產生的委託在實盤有明確、符合交易所規則的價格類型與委託價。
