## S2. 券商分點 metadata 增加 `last_attempted_date` ⏸

> **⏸ 暫緩紀錄（2026-09-17）**
> - 暫緩原因：這是純效率問題——FinMind 回 NO_DATA 時 metadata 不更新，下次會對同一區間重打。但帳號沒有券商分點權限，目前**沒有回補或日更在跑**，重複請求的實際成本為零。券商分點只回補了 5 家券商、停在 `2026-01-28`。
> - 解除條件：帳號升級、券商分點開始回補或日更，且確認要省 FinMind 額度（或 NO_DATA 重打開始影響日更時間）。

- **目的**：把「有資料到哪一天」與「已請求過到哪一天」拆成兩個欄位，已確認沒有資料的 `(broker_id, stock_id)` 區間不再重複請求。
- **現況（2026-09-15 對照程式）**：
  - metadata 由 `common.py` 的 `BrokerTradingMetadataStore` 讀寫，結構為
    `{broker_id: {stock_id: {earliest_date, latest_date}}}`，內容一律**由 DB 反推**。
    批量更新已不寫 CSV，DB ＋ metadata 是唯一的續跑依據。
  - `BrokerTradingUpdater.update()` 以 `get_existing_dates()` 展開 `earliest_date`～`latest_date`
    判斷要不要請求；`update_combination()` 回 `UpdateStatus.NO_DATA` 時只記 debug log、**不動 metadata**。
  - `refresh_from_database()` 在批次開始、每 `BATCH_UPDATE_METADATA_INTERVAL`（500）個組合、
    quota 耗盡等待前與批次結束時都會呼叫，而且**「覆寫日期範圍」與「清掉 DB 沒有的組合」都在這同一個方法內**
    ——下方第 4、5 條的兩個保留點都要改在這裡，漏改的話新欄位一個批次內就會被清掉好幾次。
- **做法**：每個 `(broker_id, stock_id)` 除了來自 DB 的 `earliest_date` / `latest_date`，再多一個 `last_attempted_date`：

  | 欄位 | 語意 | 來源 |
  |------|------|------|
  | `latest_date` | DB 裡**有資料**到哪一天 | DB |
  | `last_attempted_date` | 已向 API **請求過**到哪一天（含 NO_DATA 區間） | 請求流程 |

  1. **決定請求區間**：起始日 = `max(latest_date + 1, last_attempted_date + 1)`。
  2. **API 有資料並寫入 DB**：照現有流程從 DB 更新 `earliest_date` / `latest_date`，並把本次請求的 `end_date` 寫入 `last_attempted_date`。
  3. **API 回傳 NO_DATA**：不寫 DB，但**要更新 metadata**——把 `last_attempted_date` 設為本次請求的 `end_date`。
     注意 `load()` 有快取、只在 `refresh_from_database()` 寫檔後更新，NO_DATA 的寫入要同時更新快取與檔案。
  4. **從 DB 更新 metadata 時**（`refresh_from_database()` 前半段）：只覆寫 `earliest_date` / `latest_date`，**必須保留** `last_attempted_date`。
  5. **清理 metadata 時**（`refresh_from_database()` 後半段、刪除「DB 不存在的組合」的迴圈）：某組合在 DB 沒有任何一筆、但 metadata 有 `last_attempted_date` 時**不要刪除**——那代表「曾請求過但無資料」，刪掉下次又會從頭請求。

  第 4、5 條是最容易漏的兩處：漏了會讓 NO_DATA 的進度被靜默覆蓋或清掉，症狀是「改完之後 API 用量沒有下降」，但不會有任何錯誤訊息。
  **只有 API 正常回空表才算 NO_DATA**：2026-09-16 起 crawler 對權限不足、連線失敗一律拋例外（`FinMindRequestError`／`FinMindPermissionError`），這些情況**不可**推進 `last_attempted_date`。
- **產出**：`core/pipeline/tw/updaters/finmind/common.py`（`BrokerTradingMetadataStore`）、`core/pipeline/tw/updaters/finmind/broker_trading_updater.py`、新增測試（比照既有的 `tests/test_finmind_broker_trading_batch.py`）。
- **驗證方式**：
  1. 對一組已知無資料的 `(broker_id, stock_id)` 連跑兩次，第二次不再發出 API 請求。
  2. 先寫入 `last_attempted_date`，再觸發一次「從 DB 更新」，該欄位不變。
  3. DB 無資料但 metadata 有 `last_attempted_date` 的組合，在清理後仍存在。
  4. 既有 metadata 檔（沒有 `last_attempted_date` 欄位）可以直接讀入，行為與現在相同。
- **相依**：無。範圍只限券商分點的 metadata 讀寫，不動其他 FinMind 資料集、不改 DB schema、不做爬取並行化。

### 附：方案比較

- **做法一：metadata 增加 `last_attempted_date`（採用，即 S2）**。語意清楚、不會重複打已知無資料的區間；資料若延遲上架可能漏掉，需搭配 S3 或定期 backfill。
- **做法二：NO_DATA 時把 `latest_date` 推到 `end_date`（不採用）**。實作最小，但 `latest_date` 的語意會變成「有資料**或**已檢查到這天」，從 DB 更新時必須取兩者較大值，一旦忘記就是靜默錯誤；且 `refresh_from_database()` 的清理迴圈會刪掉 DB 沒有任何一筆的組合，做法二對「從未有資料」的組合依然無效。
- **業界慣例**：watermark／cursor 在「無資料」時也前進；區分 last_success 與 last_attempted；對 NO_DATA 區間設 N 天後重試或定期 backfill。不建議對同一段已知無資料的區間每次都重打（＝目前行為）。

## S14. 當沖三段式：回測引擎 ⏸

> **⏸ 暫緩紀錄（2026-10-08）**
> - 暫緩原因：使用者裁示。實盤開盤段的進出場在同一次集合競價撮合，拿不到「先平後開」的好處，回測改了只會比實盤樂觀（見下方〈暫緩理由〉）。
> - 解除條件：實盤出現能「先確認回補成交、再開倉」的段落（例如盤中逐筆），且回測能模擬同樣的先後時，再重新評估；或使用者另行指示。
> - 恢復時：從本步驟開始，完成後接 S15，須重產放空 baseline。
> - **2026-10-18 複查**：解除條件仍未成立。`feature/tick-backtest` 起回測多了逐筆重放的 `TickSimulator`、實盤有盤中迴圈（`盤中動能策略.md`），
>   但兩者的開平倉先後仍只由 `order_rules.get_execution_sequence()` 推導，沒有「先確認回補成交、再開倉」的段落。`盤中動能策略.md` 的回測假設表也引用本步驟（隔天開盤出場的部位要等新倉開完才賣，偏保守）。

**背景**：同一根 bar 的開平倉順序只由 `allow_day_trade` 推導。當沖策略走「先開倉、再平倉」，今天要平掉的**隔夜部位**要等新倉開完才賣得掉，釋出的資金與持倉名額趕不上當天開倉。三段式改為：① 先平隔夜部位 → ② 開新倉 → ③ 檢查當天新開的部位要不要平；不當沖策略維持「先平後開」。**不新增策略設定欄位**（順序仍只由 `allow_day_trade` 推導）、不改停損與一般平倉的相對順序、不改結算層的日終強制回補。驗收標準：回測與實盤用同一份順序規則；`ForeignSellingReversalShortStrategy` 的差異只出現在有隔夜部位的交易日且逐日說明得出原因。

- **目的**：讓隔夜部位先出場，釋出的資金與持倉名額可供當天開倉。
- **落點（2026-10-18 對照程式）**：main 的開平倉先後在 `Backtester.execute_bar()`；`feature/tick-backtest` 起 `Backtester` 只留逐日迴圈，
  日 K 的先後在 `BarSimulator.process_bar()`（`core/backtest/simulator/bar_simulator.py`），逐筆回測在 `TickSimulator`（同目錄 `tick_simulator.py`）也依同一個
  `get_execution_sequence()` 分支，回傳型別是 `BarExecutionSequence`（`OPEN_THEN_CLOSE`／`CLOSE_THEN_OPEN`）。恢復時以合併後的 simulator 為準，兩個 simulator 都要改。
- **做法**：開平倉先後的執行處（見上方落點）在 `allow_day_trade=True` 時改為三段：
  1. 平倉階段只處理**開倉日早於今天**的部位；
  2. 開倉階段；
  3. 平倉階段只處理**今天新開**的部位。

  第 1、3 段都呼叫同一個 `generate_close_signals()`，引擎以部位的開倉日過濾訊號，**策略不需要改**。須確認策略不會因為同一根 bar 被呼叫兩次平倉鉤子而重複累計內部狀態。
- **產出**：main 為 `core/backtest/backtester.py`；`feature/tick-backtest` 合併後為 `core/backtest/simulator/bar_simulator.py`、`tick_simulator.py`；`order_rules.get_execution_sequence()` 與 `BarExecutionSequence`（`core/utils/constant/engine.py`）可能要從兩值擴成三值，或改成回傳階段序列。
- **驗證方式**：新增測試：持有一筆隔夜空單、資金只夠再開一筆時，三段式下當天開得了新倉；不當沖策略的回測結果逐筆不變。
- **相依**：無（影響面已於原文件 S1 量測完畢，見下方〈附：影響面量測〉）。

### 暫緩理由（2026-10-08 使用者裁示）

設計 S14、S15 時逐項推演（第 ③ 段只看當天新倉、停損放哪一段、實盤段落怎麼對應），發現**三段式的好處在實盤拿不到**：

1. **實盤沒有真正的先後**：開盤段 08:30～08:59 送單，09:00 開盤集合競價一起撮合。決定開幾檔的當下，隔夜部位的回補單還沒成交，
   部位仍在帳上，實盤的持倉檢查（含未終結委託）照樣佔一個名額——〈附：影響面量測〉量到的那 3 天，實盤仍只會開 4 檔。
   要讓實盤也多開，只能假設回補一定成交；但隔夜部位正是前一天鎖漲停補不到才留下的，再鎖一次就會超過持倉上限。
2. **回測因此比實盤樂觀**：回測知道回補成交、釋出名額，實盤不知道。parity 在那幾天必有差異，違反本文件「回測與實盤用同一份順序規則」的驗收標準。
3. **其他推演出的問題**：
   - 引擎規則是通用的：以收盤價判斷隔夜部位去留的策略，第 ① 段會在開倉前用到收盤資料（偷看未來），引擎擋不住。
   - 第 ① 段平掉後第 ② 段可重開同一檔，實盤決策當下仍持有、不會重開——又一個分岔。
   - 實盤開盤段讀不到開盤價（`PreOpenStockQuote` 讀 OHLC 會拋錯），而 `ForeignSellingReversalShortStrategy` 的隔夜回補要用開盤價，策略本身得改寫。
   - 放空回補要付錢、融券擔保價款與保證金交割後才退回，「先平再開釋出資金」對空單主要只成立在名額。
4. **結論**：「先出場再進場」只在**出場確定先成交**的環境才是常見做法；台股日頻策略的進出場擠在同一次集合競價，維持現行
   「當沖先開後平」讓回測與實盤一致，而且只會偏保守。

**解除條件**：實盤出現能「先確認回補成交、再開倉」的段落（例如盤中逐筆），且回測能模擬同樣的先後時，再重新評估；或使用者另行指示。

## S17. 債券 ETF 證交稅停徵 ⏸

- **目的**：被動式債券 ETF 的證交稅目前停徵（2017-01-01～2026-12-31），成本模型一律以 ETF 的 0.1% 計，交易債券 ETF 時會高估成本。
- **做法**：`calculate_transaction_tax()` 在 ETF 分支內再分債券 ETF（代號 `00` 開頭、`B` 結尾），依成交日落在停徵區間就課 0；槓桿型、反向型債券 ETF 不適用停徵。停徵區間的起訖日放在 `core/utils/constant/cost.py`，比照當沖減半的 `DAY_TRADE_TAX_START`／`DAY_TRADE_TAX_EXPIRY`。
- **產出**：上述兩檔與測試。
- **驗證方式**：停徵期間內外、槓桿／反向各一條測試；拿掉即轉紅；不交易債券 ETF 的策略回測零變動。
- **相依**：無程式相依。**動工前先查證停徵期限**：2026-10-29 查得行政院已於 2026-10-01 通過延長到 2036-12-31 的修正草案（並把主動式債券 ETF 自 2027-01-01 納入），立法院尚未三讀；以動工當時的法規為準。
