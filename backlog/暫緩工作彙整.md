## S2. 券商分點 metadata 增加 `last_attempted_date` ⏸

> **⏸ 暫緩紀錄（2026-09-17）**
> - 暫緩原因：這是純效率問題——FinMind 回 NO_DATA 時 metadata 不更新，下次會對同一區間重打。但帳號沒有券商分點權限，目前**沒有回補或日更在跑**，重複請求的實際成本為零。券商分點只回補了 5 家券商、停在 `2026-01-28`。
> - 解除條件：帳號升級、券商分點開始回補或日更，且確認要省 FinMind 額度（或 NO_DATA 重打開始影響日更時間）。

- **目的**：把「有資料到哪一天」與「已請求過到哪一天」拆成兩個欄位，已確認沒有資料的 `(broker_id, stock_id)` 區間不再重複請求。
- **現況（2026-09-15 對照程式）**：
  - metadata 由 `common.py` 的 `BrokerTradingMetadataStore` 讀寫，結構為
    `{broker_id: {stock_id: {earliest_date, latest_date}}}`，內容一律**由 DB 反推**。
    批量更新已不寫 CSV，DB ＋ metadata 是唯一的續跑依據。
  - `BrokerTradingUpdater.update()` 以 `get_existing_dates()` 展開 `earliest_date`～`latest_date`
    判斷要不要請求；`update_combination()` 回 `UpdateStatus.NO_DATA` 時只記 debug log、**不動 metadata**。
  - `refresh_from_database()` 在批次開始、每 `BATCH_UPDATE_METADATA_INTERVAL`（500）個組合、
    quota 耗盡等待前與批次結束時都會呼叫，而且**「覆寫日期範圍」與「清掉 DB 沒有的組合」都在這同一個方法內**
    ——下方第 4、5 條的兩個保留點都要改在這裡，漏改的話新欄位一個批次內就會被清掉好幾次。
- **做法**：每個 `(broker_id, stock_id)` 除了來自 DB 的 `earliest_date` / `latest_date`，再多一個 `last_attempted_date`：

  | 欄位 | 語意 | 來源 |
  |------|------|------|
  | `latest_date` | DB 裡**有資料**到哪一天 | DB |
  | `last_attempted_date` | 已向 API **請求過**到哪一天（含 NO_DATA 區間） | 請求流程 |

  1. **決定請求區間**：起始日 = `max(latest_date + 1, last_attempted_date + 1)`。
  2. **API 有資料並寫入 DB**：照現有流程從 DB 更新 `earliest_date` / `latest_date`，並把本次請求的 `end_date` 寫入 `last_attempted_date`。
  3. **API 回傳 NO_DATA**：不寫 DB，但**要更新 metadata**——把 `last_attempted_date` 設為本次請求的 `end_date`。
     注意 `load()` 有快取、只在 `refresh_from_database()` 寫檔後更新，NO_DATA 的寫入要同時更新快取與檔案。
  4. **從 DB 更新 metadata 時**（`refresh_from_database()` 前半段）：只覆寫 `earliest_date` / `latest_date`，**必須保留** `last_attempted_date`。
  5. **清理 metadata 時**（`refresh_from_database()` 後半段、刪除「DB 不存在的組合」的迴圈）：某組合在 DB 沒有任何一筆、但 metadata 有 `last_attempted_date` 時**不要刪除**——那代表「曾請求過但無資料」，刪掉下次又會從頭請求。

  第 4、5 條是最容易漏的兩處：漏了會讓 NO_DATA 的進度被靜默覆蓋或清掉，症狀是「改完之後 API 用量沒有下降」，但不會有任何錯誤訊息。
  **只有 API 正常回空表才算 NO_DATA**：2026-09-16 起 crawler 對權限不足、連線失敗一律拋例外（`FinMindRequestError`／`FinMindPermissionError`），這些情況**不可**推進 `last_attempted_date`。
- **產出**：`core/pipeline/tw/updaters/finmind/common.py`（`BrokerTradingMetadataStore`）、`core/pipeline/tw/updaters/finmind/broker_trading_updater.py`、新增測試（比照既有的 `tests/test_finmind_broker_trading_batch.py`）。
- **驗證方式**：
  1. 對一組已知無資料的 `(broker_id, stock_id)` 連跑兩次，第二次不再發出 API 請求。
  2. 先寫入 `last_attempted_date`，再觸發一次「從 DB 更新」，該欄位不變。
  3. DB 無資料但 metadata 有 `last_attempted_date` 的組合，在清理後仍存在。
  4. 既有 metadata 檔（沒有 `last_attempted_date` 欄位）可以直接讀入，行為與現在相同。
- **相依**：無。範圍只限券商分點的 metadata 讀寫，不動其他 FinMind 資料集、不改 DB schema、不做爬取並行化。

### 附：方案比較

- **做法一：metadata 增加 `last_attempted_date`（採用，即 S2）**。語意清楚、不會重複打已知無資料的區間；資料若延遲上架可能漏掉，需搭配 S3 或定期 backfill。
- **做法二：NO_DATA 時把 `latest_date` 推到 `end_date`（不採用）**。實作最小，但 `latest_date` 的語意會變成「有資料**或**已檢查到這天」，從 DB 更新時必須取兩者較大值，一旦忘記就是靜默錯誤；且 `refresh_from_database()` 的清理迴圈會刪掉 DB 沒有任何一筆的組合，做法二對「從未有資料」的組合依然無效。
- **業界慣例**：watermark／cursor 在「無資料」時也前進；區分 last_success 與 last_attempted；對 NO_DATA 區間設 N 天後重試或定期 backfill。不建議對同一段已知無資料的區間每次都重打（＝目前行為）。

## S3. 券商分點 NO_DATA 區間的延遲重試（可選） ⏸

> **⏸ 暫緩紀錄（2026-09-17）**：與 S2 相同的外部條件，且相依 S2。

- **目的**：S2 會讓「資料延遲上架」的區間永遠不再被請求；對曾回傳 NO_DATA 的區間在 N 天後再試一次。
- **做法**：新增 `recheck_no_data_after_days`（建議 7／14／30）；若 `(today - last_attempted_date).days >= N`，允許重新請求該區間。
- **產出**：同 S2。
- **驗證方式**：把 `last_attempted_date` 手動調到 N 天前，重跑時該區間被重新請求；未滿 N 天時不請求。
- **相依**：S2。

## S4. 股票期貨行情：前 N 檔定義與回補 ⏸

> **⏸ 暫緩紀錄**
> - 2026-09-13 使用者依成本估算裁示暫緩；2026-09-15 複查確認現階段不需要補爬。
> - 暫緩原因：沒有使用端——`core/strategies/futures/` 只有 `MomentumFuturesStrategy`（預設 TX、日線），沒有任何策略交易股票期貨；回測只從 `futures_stock_universe` 讀股期乘數，該表已有資料，不需要行情。
> - 解除條件：**開始開發股期策略**時再開跑，建議先取小範圍（前 10 檔 × 2020 起，約 2.5 天），有需要再往前延伸。
> - **2026-09-18 補充**：下方做法第 1、2 點已依當日的程式修正改寫。起因是預設的 `python -m tasks.update_db` 曾含 `futures_stock_price` 並踩中 fallback，對 320 檔從 2015 年起回補。當日已完成三件事：`futures_stock_price` 移出 `all`／`no_tick`；`resolve_stock_futures_products()` 的 fallback 由「退回整份標的池」改為「取標的池前 `top_n` 檔」；中斷留下的 CAF 半段行情已刪除（8,500 列、1,730 個中繼檔）。

- **目的**：`futures_stock_universe` 有 640 列快照（個股期貨 498、小型個股期貨 94、ETF 期貨 42、小型 ETF 期貨 6），對應 320 檔商品，但 `futures_price_daily` 只有三檔驗證足跡（CDF 2 日、NYF 2 日、EEF 1 日，2026-08-27~08-28），**回補從未開始**（2026-09-18 一次誤觸留下的 CAF 1,700 日已刪除，表內重新只剩這三檔）。
- **成本估算**：`FuturesPriceUpdater.crawl_and_clean_date()` 每個「商品 × 日」固定打日盤＋夜盤 **2 次請求**（夜盤查無資料也照打），速度約 **6.3 秒/次**。這是由 `settings.py` 註解「六檔歷史回補約需 40 小時」與六檔實際入庫日數（約 2.3 萬次請求）反推，**不是逐筆實測**；updater 的節流常數（每次 3~6 秒、每 50 次休 120 秒）算出來也是同一量級。

  | 範圍 | 請求數 | 預估耗時 |
  |------|-------:|---------:|
  | 前 20 檔 × 2015 起（`STOCK_FUTURES_TOP_N` 現值） | 約 11.4 萬 | 8~9 天 |
  | 前 20 檔 × 2020 起 | 約 6.6 萬 | 約 5 天 |
  | 前 10 檔 × 2020 起 | 約 3.3 萬 | 約 2.5 天 |

- **做法**：
  1. **先暖身，不要直接開跑**：`--target futures_stock_price` 走 `FuturesPriceUpdater.update_stock_futures()` → `resolve_stock_futures_products()`。有 `STOCK_FUTURES_TOP_N`（現值 20）時會呼叫 `FuturesStockUniverseAPI.get_top_liquid_products()`，它要求每檔至少 `min_days=5` 個交易日的日盤行情；表內三檔股期只有 1~2 日，排序結果為空。**此時會取標的池的前 `top_n` 檔當暖身樣本**（2026-09-18 修正後的行為；在那之前是退回整份 320 檔），順序依商品代碼、不是流動性。暖身二擇一：
     - `python -m tasks.update_db --target futures_stock_price --from <近 5 個交易日前>`：20 檔 × 5 日約 200 次請求、20 分鐘左右。樣本是標的池的頭 20 檔（`CAF`、`CBF`、`CCF`…），不保證是量大的那批。
     - 以 `update_stock_futures(products=[...])` 直接指定候選商品（優先於 `top_n`），只對候選清單暖身。**想要暖身樣本貼近真正的高流動性標的就走這條**。
  2. 暖身後確認 `get_top_liquid_products()` 排得出**足夠檔數**（不是只回傳一兩檔——那代表暖身樣本裡只有少數幾檔真的有量，排序沒有代表性），再定 N 與起點（`settings.py` 已定案「股票期貨預設只爬流動性前 N 檔」，理由見該處註解），寫進 `core/config/settings.py` 後開正式回補。開跑前 updater 會把估算的請求量寫進 log，對不上預期就先停。
  3. 逐商品例外隔離已於 2026-09-13 完成（`update()` 跑完才拋 `ProductUpdateError`），上市晚於起點的商品不會中止整批。
- **產出**：`core/config/settings.py` 前 N 檔設定與選取依據的註解；回補執行。
- **驗證方式**：N 檔在 `futures_price_daily` 各有連續序列且對照基準日曆零缺口；抽樣一檔比對除權息日的乘數調整正確。
- **相依**：無。解除時若同時有其他交易所回補在跑，注意共用 TAIFEX 請求節奏，不要同時跑。

## S6. 漲跌停改用公告值 ⏸

> **⏸ 暫緩紀錄（2026-09-17 立項、2026-09-18 移入本文件）**
> - 暫緩原因：同 S5，卡公告值資料源。
> - 解除條件：來源盤點完成；或出現真的依賴漲停判定的策略。
> - **2026-10-01 已解除**：來源盤點完成（見 S5 章節〈來源盤點紀錄〉），狀態改為 ⬜ 可開工。
> - 出處：原 `docs已載明但未實作的缺口盤點.md` S9。

- **目的**：`TwStockSpec.get_price_limits()` 以「前收 ±幅度後往內對齊檔位」推算漲跌停，**與交易所公告值多數差一檔**（2026-08-15 實測 23,972 筆，相符率 61.6%）。影響 `FillModel.validate()` 的邊界拒單與 `TwStockSettlementModel.check_limit_up_locked()` 的鎖漲停判定（進而影響 `limit_up_cover_failed` 計數）——也就是放空策略最致命的那個尾部風險的計數會偏。

> **2026-10-01 來源盤點時重新量測，修正上方「相符率 61.6%、落差來自檔位對齊規則」的判斷**：
> 以 `TWT84U` 2024-01-02 的公告值，**改用公告的「開盤競價基準」當輸入**呼叫 `TwStockSpec.get_price_limits()`：
>
> | 類別 | 檔數 | 公式與公告完全相符 |
> |------|-----:|------:|
> | 普通股（四碼、非 `00` 開頭） | 1,001 | **97.9%**（980 檔） |
> | ETF（`00` 開頭，排除無漲跌幅者） | 53 | **18.9%**（10 檔） |
>
> 剩下的落差有兩個**具體、可修的原因**，都不是「檔位規則與交易所不一致」：
> 1. **浮點誤差**：`15.5 × 0.9` 在浮點數是 `13.950000000000001`，往上對齊檔位後變成 14.0（公告 13.95）；42 × 0.9、104 × 0.9 同理。
>    `StockUtils.round_to_tick()` 內部用 `Decimal`，但乘法在轉 `Decimal` **之前**就以浮點做完了。普通股不符的 21 檔樣本都是這一型。
> 2. **ETF 套用了普通股的升降單位表**：例如 0050 基準 135.45，公告漲停 148.95、公式 148.5——ETF 的檔位較細。
>
> 2026-08-15 那次 61.6% 的量測口徑（用哪個基準價、含不含 ETF）沒有留下紀錄，與本次差異的來源無法逐筆對照；
> 但本次以公告基準為輸入，已可排除「基準價」這個變數。
> **含意**：公告值仍是正確答案（本步驟照做），但公式版的 fallback 修掉上述兩點後就幾乎與公告一致。
> 修正會改變邊界上的拒單與 `limit_up_cover_failed` 計數（屬「改變回測結果」，要重產 baseline），**另立工作、不在本步驟順手改**；
> `TwStockSpec.get_price_limits()` 的 docstring 對落差原因的描述也要一併更正。
>
> **✅ 公式修正已完成（2026-10-01，與 S6 同批）**：
> - `InstrumentSpec.scale_price()`：「價格 × (1 ± 幅度)」改以 `Decimal` 計算後才轉回 float，漲跌停與滑價共用。

收斂的判準是**把「該重試的傳輸失敗」與「該讓人看的程式錯誤」分開**，
而不是逐一列舉例外名稱：

| 位置 | 原本 | 改為 | 理由 |
|---|---|---|---|
| `_crawl_listing_boards()` 送出請求 | `except Exception` | `except OSError` | `requests` 的例外與作業系統層的 `ConnectionError` 都繼承 `OSError`，一條涵蓋所有傳輸失敗；payload 組錯拋的 `TypeError` 則會現形，不再退化成「整季視為失敗」後每次重跑都以警告收場 |

| `_request_equity_changes()` 解析表格 | `except ValueError` | `except self.HTML_PARSE_ERRORS` | **既有的收窄不足，順帶修掉**；見下 |

**「HTTP 200 但 body 全空」是漏接的那一種**：`pd.read_html("")` 拋的是 lxml 的
`XMLSyntaxError`，它繼承 `SyntaxError` 而**不繼承 `ValueError`**（2026-09-25 實測，
其餘壞內容才是 `ValueError`）。權益變動表那一處原本只收 `ValueError`，於是空 body
