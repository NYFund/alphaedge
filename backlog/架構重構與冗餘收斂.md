# 架構重構與冗餘收斂

## Abstract

**背景／問題**：全專案盤點（`core`＋`tasks`＋`run.py` 共 391 個 Python 檔、約 58,000 行；
另含 `tests` 42,907 行、`scripts`／`frontend`／`strategy_lab` 共 32 檔）後，
發現的問題集中在**一個系統性成因**：專案的基底類別把「流程骨架」宣告成 `@abstractmethod`
而不提供具體實作，於是每個子類自己抄一份。已量化的後果——12 個 API 的建構程式碼逐字相同、
10 個 loader 的 `disconnect()` 本體逐字相同、3 支台股日頻 updater 兩兩相似度 70~81%（正規化後最高 89.5%）、
`core/backtest/report/base.py` 是「13 個抽象方法、0 個實作」的空殼。
這不是理論風險：`stock_price_loader` 的入庫流程已經比 `stock_chip_loader`／`stock_margin_loader`
多出四項改進（含檔內主鍵去重），另外兩份至今沒跟上。

同一個成因的另一面是**共用契約擺錯位置**：`BaseDataFeed` 與三個市場結構模組住在
`core/backtest/datafeed/` 底下，但實盤、ETL、策略層都要用它們，
`scripts/check_layer_deps.py` 的 `_KNOWN_REVERSE` 四條反向相依中有三條出自這裡；
`core/adapters/` 則反過來——純轉換層自己查資料庫，讓它相依 `core.api`。

**但本份最高優先的不是重複，是 `core/live/` 的四道「寫好了卻沒人呼叫」的安全檢查**：
`verify_data_freshness()`、`is_market_open()`、`check_daily_loss()`、`verify_quota()`
程式與單元測試都完成，正式路徑上**零呼叫點**。最直接的證據是一條死掉的錯誤路徑——
`DataFreshnessError` 只在 `verify_data_freshness()` 內拋出，而 `run.py:242` 特地接住它回
`EXIT_STALE_DATA`（結束碼 3），**所以結束碼 3 永遠不會發生**。
另有一處必定 crash：`AccountSynchronizer` 無條件建 `StockOrder`，期貨第一筆成交進
`apply_fill()` 就會 `AttributeError`。兩者都不是重構，是實盤的 correctness 缺口，
只是在同一次盤點中撈出來，故併入本份（Phase7-1、Phase7-2）。

**目標**：

1. 把共用契約與市場結構搬到中立套件（`core/datafeed/`、`core/market/`），反向相依歸零。
2. 把 `core/adapters/` 收斂成零 I/O 的純轉換層（吃 DataFrame、回 Quote），並依業界常見的
   ports & adapters 分工，把「來源特有的欄位解析」與「來源無關的報價健檢」拆開，
   讓回測（股票與期貨）與實盤三條路徑共用同一份健檢規則。
3. 以 `BaseDataFeed` 為範本（**它是專案裡唯一做對的基底**），把另外四個基底的流程骨架收回。
4. 拆開職責混雜的大檔，清掉死碼與冗餘設定，修正會造成假綠燈的文件脫節與防呆缺口。
5. 接上 `core/live/` 四道沒人呼叫的安全檢查、修掉期貨帳戶同步的訂單型別，
   並趁 `LiveTrader` 再長大之前把盤後生命週期拆出去。
6. 讓回測與實盤對**同一條規則只有一份實作、且兩邊都真的呼叫**：
   接上 `check_max_holdings()` 的實盤呼叫端，並把各寫一份的單一標的曝險上限收斂成一條公式。

**範圍界線（不做）**：

1. **不動策略介面**：`BaseStrategy.setup_apis(feed)` 的型別、`BaseDataFeed` 的方法簽章一律不變，只換 import 路徑。
2. **不把券商端的報價轉換搬進 `core/adapters/`**：`ShioajiQuoteStream.to_stock_quote()` 是
   Shioaji SDK 的 anti-corruption layer，留在 `core/broker/`（理由見 Phase3-4）。
3. **不合併 `stock_*` 與 `futures_*` 兩條平行實作**。實測相似度：`position_manager` 9.7%、
   datafeed 8.7%、reporter 14.6%、quote adapter 0%。那是真實的領域差異
   （股票是「現金換標的」、期貨是「凍結保證金＋逐日盯市」），`BasePositionManager` 已經把
   FIFO 主幹抽走，抽得剛好。**唯一例外是 `core/models/` 的 quote（59%）**，由 Phase3-6 收斂。

   `record.py`（stock 80 行 ↔ futures 76 行，逐字相同 39 行）**刻意不收斂**：
   它重複的是 `__init__` 明確列出每個參數再轉發給 `super().__init__()` 的樣板，
   收斂就得改用 `**kwargs`，而 CLAUDE.md §2.4 要求所有參數標註型別、可選欄位一律
   `Optional[T]` 並給預設值。**那是專案刻意付的代價，換來 IDE 補全與型別檢查**，
   與 `PreOpenQuote` 重複了三個微妙陷阱的性質完全不同。
4. **不重構 `MarketCalendar` 的建構形狀**（收 API 物件 → 收交易日清單，向 `FuturesCalendar` 看齊）。
   同一類耦合，但獨立於本份，見〈已知但本份不做〉。
5. **不新增市場、不新增商品**：美股落點見 [美股ETL與回測架構規劃.md](美股ETL與回測架構規劃.md)，
   本份只負責把它要接的掛點擺對位置。
6. **不重複 [實盤下單架構規劃.md](實盤下單架構規劃.md) 已排程的項目**：
   `core/utils/{order,callback,account}.py` 的刪除屬該文件 Phase7-3，
   `core/live/` 的功能缺口（盤後作業、盤中迴圈、parity 比對）屬該文件 Phase4~Phase5。
   本份只處理 `core/live/` 的**結構性重複與冗餘**，且一律標明與該文件的分界。
7. **不改任何交易邏輯**：本份全程要求 `./scripts/run_regression.sh` 回歸雙線**逐筆零變動**，
   **38 個步驟無一例外**。唯一會改變回測結果的是
   `FuturesBacktestReporter` 改繼承方向，而它列在〈已知但本份不做〉第 6 點、不在本份範圍內。

**驗收標準**：

1. `python scripts/check_layer_deps.py` 違規總數 0，且 `_KNOWN_REVERSE` 清空為 `{}`。
2. `core/adapters/` 不 import `core.api`，F 區的 adapter 相關邊消失；
   `core/portfolio` → `core.managers` 與 `core/managers` → `core.backtest.models` 兩條邊消失。
   **`core/live` → `core.backtest.models` 不在本份範圍**——`core/live/factory.py:304,316` 用的是
   `StockCostModel`／`TwFuturesCostModel` **本體**、`:307,319` 用 `TwStockSpec`／`TwFuturesSpec`，
   那是 D0「策略層不分家」的直接後果（實盤與回測共用同一套成本與契約規格），抽 dataclass 消不掉，
   也不該消掉。
3. `./scripts/run_regression.sh` 回歸雙線逐筆相同，**38 個步驟全部適用、無例外**。
4. 新增的報價健檢層同時被回測（股票 ＋ 期貨）與實盤兩條路徑呼叫，並有守門測試確保口徑一致。
5. 四個基底（`BaseDataAPI`、`BaseDataLoader`、`BaseDataUpdater`、`BaseFillModel`）的
   `@abstractmethod` 只剩「子類本體確實互異」的那些，其餘改為具體實作或有預設的 hook。
6. `pyproject.toml` 的 `ruff` ignore 清單數量註記與現查值一致。
7. `core/execution/order_preprocess.py` 的每個公開函式都有**回測與實盤兩個呼叫端**，
   或在該函式的 docstring 明寫為何只有一邊適用。

## 這份工作的判準：`BaseDataFeed` 是範本

動手前先把判準講清楚，否則「收回骨架」會被做成「把 `@abstractmethod` 全刪掉」——
那更糟：現在子類漏實作會在**實例化當下** `TypeError`，刪掉裝飾器後會變成靜默的 no-op。

`core/backtest/datafeed/base.py`（178 行）是專案裡唯一做對的基底，三種方法各司其職：

| 類別 | 判準 | `BaseDataFeed` 的例子 |
|------|------|----------------------|
| **真抽象** | 子類本體確實互異 | `setup()`、`is_market_open()`、`get_quotes()`（3 個） |
| **具體實作** | 子類本體逐字相同 | — |
| **有預設的 hook** | 多數子類不必覆寫 | `close()` 預設 no-op、`get_price_limit_basis()` 預設回 `{}`、另外 5 個同形（7 個） |

三者傳達的意思完全不同：

```python
@abstractmethod
def get_quotes(self, ...) -> List[BaseQuote]: ...     # 「你一定要想過這件事」

def disconnect(self) -> None:                          # 「不用管，我處理好了」
    ...

def get_price_limit_basis(self, date) -> Dict[str, float]:   # 「通常不用管，要改再覆寫」
    return {}
```

另外四個基底的毛病是**三種意思全部寫成了第一種**。最極端的是
`BaseDataLoader.create_db()`：7 個子類的本體都是同一行 `self.dao.create_table()`，
而基底把它宣告成抽象方法，等於對 loader 作者說「關資料庫這件事你得自己想」。

**Phase1-1 把 `BaseDataFeed` 搬到 `core/datafeed/` 之後，它就是 Phase4 的現成範本。**
這也是本份把兩件事合併成一份文件的理由：它們是同一個問題的兩面。

### Phase3-2. 報價健檢抽成來源無關層，期貨與實盤路徑一併套用 ⬜

- **目的**：**這是本份工作裡唯一可能擋下真實錯誤的一步。**

  `StockQuoteAdapter` 累積了三條報價健檢規則，每一條的註解都記著一個踩過的坑：

  | 規則 | 防的是什麼 |
  |------|------------|
  | `has_valid_price()` | 無成交日的 OHLC 是 NULL（舊 cleaner 填成 0），不濾掉會用 0 元成交 |
  | `warn_duplicate_symbols()` | 上市股與上櫃 ETF 共用 4 碼代號，`quote_map` 只留最後一筆，成交價與訊號都可能取到另一檔商品 |
  | TICK 分支必帶 `cur_price`／`close`／`volume` | 舊版只掛 `tick=`，所有讀 `quote.close` 的地方都拿到 0 元 |

  **另外兩條路徑一條都沒有**：

  1. **實盤**（`core/broker/tw/shioaji_quote_stream.py:219` 的 `to_stock_quote()`）
     用 `float(getattr(snapshot, "close", 0.0) or 0.0)`——停牌或快照缺值時，
     回測會濾掉這檔，實盤會拿到一個 0 元的 `StockQuote`。
  2. **期貨回測**（`core/adapters/tw/futures_quote_adapter.py`）**完全沒有重複代號偵測**。
     現查：`grep -rn "warn_duplicate_symbols" core/` 在該檔 **0 命中**。
     而 `backtester.py:660` 對期貨同樣建 `quote_map: Dict[str, BaseQuote] = {q.symbol: q for q in quotes}`，
     期貨的 `symbol` 是 `f"{product}{expiry}"`——日盤／夜盤同契約、`FuturesSession.COMBINED`
     合併失敗、或週契約與月契約代號碰撞，都會**靜默只留最後一筆**。

- **做法**：

  1. 新增 `core/adapters/quote_validation.py`，**模組層級純函式**
     （比照 `core/live/risk/` 的金額與曝險規則寫法：連實例都不必建就測得動）：

     ```python
     def has_valid_price(close: Optional[float]) -> bool: ...
     def find_duplicate_symbols(quotes: Sequence[BaseQuote]) -> List[str]: ...
     def warn_duplicate_symbols(quotes: Sequence[BaseQuote], date: datetime.date) -> None: ...
     ```

     簽章**吃值不吃列**（`close: Optional[float]` 而不是 `row: Any`），這樣它與來源的欄位名完全無關，
     `price` 表、Shioaji `Snapshot`、期貨 `futures_price` 表都能套。

  2. `StockQuoteAdapter` 改為呼叫這層，刪掉自己那份。
  3. **`FuturesQuoteAdapter` 首次套用**：`generate_futures_quotes()`（`:220`）與
     `convert_to_combined_quotes()`／`combine_sessions()`（`:105`）各呼叫一次
     `warn_duplicate_symbols()`。**首次啟用可能噴出一批既有 warning，要先跑一次分辨
     哪些是真問題、哪些是 `COMBINED` 模式的預期行為**——若全部是預期的，該模式要在呼叫前排除，
     而不是把規則關掉。
  4. `ShioajiQuoteStream.to_stock_quote()` / `to_futures_quote()` 套用同一層：
     `close` 無效時**回 `None` 讓呼叫端略過該檔並記 warning**，不要回一個 0 元報價。
     `get_snapshots()` 的回傳因此會少掉查無資料的標的——這與 `_build_pre_open_quotes()`
     對取不到參考價的處理一致（`stock_live_datafeed.py:180`，「略過而不是給 0」）。
  5. **`warn_duplicate_symbols()` 維持只警告不排除**：要留哪一筆屬資料修正範疇，

### Phase4-1. `BaseDataAPI` 收回建構骨架（12 個 API）✅

- **目的**：`self.owns_conn: bool = conn is None` 在 `core/api/tw/*.py` **12 檔逐字命中**，
  `connect_sqlite(...)` 12 檔各一次，`LogManager.setup_logger(..., log_dir=API_LOGS_DIR_PATH, ...)` 13 檔各一次。
  每支 API 的 `__init__` ＋ `setup()` 是同一段 20 行，只差 DAO 類別與 log 檔名。

  `core/api/base.py` 的 `close()`（`:52`）**已經在讀 `self.owns_conn`**——這個約定基底是知道的，
  但 `setup()` 仍宣告為 `@abstractmethod`（`:18`），於是「開」那一半每支都自己寫。
  **只管關不管開**是這個基底最清楚的症狀。

- **做法**：

  1. `BaseDataAPI` 新增三個類別屬性與一個具體 `__init__(conn=None)`：

     ```python
     class BaseDataAPI(ABC):
         DAO_CLASS: Type[BaseDAO]
         DEFAULT_DB_PATH: Path
         LOG_FILE_NAME: str
     ```

  2. `setup()` 由抽象改為具體實作（開 conn、setup logger），需要額外設定的 API 覆寫後呼叫 `super().setup()`。
  3. 12 個子類只留三個常數 ＋ `get_*` 業務查詢方法。
  4. **`stock_tick_api.py` 排除在外**：它走 DolphinDB 不走 SQLite，現查 `owns_conn` 0 命中，本來就不同形。

- **產出**：`core/api/base.py`、`core/api/tw/` 12 檔。預估減少約 200 行。

- **驗證方式**：`tests/test_api_public_interfaces.py` 明確盯住這批類別的公開方法簽章，是現成回歸網；
  `python scripts/check_api_orphan_methods.py` 通過；回歸雙線逐筆相同。

- **相依**：無。**主題四從這步起手**——四個基底裡它影響面最廣但風險最低，
  且 `tests/test_api_public_interfaces.py` 是現成守門測試。

  日頻模式下三個段落是三個獨立行程，本地帳每次都從零開始——
  **`RiskConfig.daily_loss_ratio`（3%）因此形同虛設**。

- **為什麼是暫緩不是待辦**：三條可選解都有各自的前置，而其中兩條要等別的東西先到位。

  | 方案 | 可用性 | 代價 |
  |---|---|---|
  | 取 `BrokerPositionSnapshot.unrealized_pnl` | 立刻（`rebuild_from_broker()` 收到的那批就有） | 對帳不一致時，這道檢查與本地帳會給出不同答案 |
  | 由 `live_account_snapshot` 比對昨日 `total_equity` | 要先確認該表每天都寫得到 | 盤後作業沒跑的那天就沒有基準值 |
  | `recover()` 回放當日已成交回報 | 要動 OMS 重啟路徑 | 風險最高，且開盤段（當天還沒成交）依然是 0 |

  > **方案二的前提在 2026-09-22 才補齊**：紀錄庫的時間欄位原本只存日期，
  > 「昨天那筆快照」與「今天這筆」在 DB 裡分不出先後，取基準值要靠猜。
  > 已由 [專案優化與改善清單.md](專案優化與改善清單.md) Phase1-2 改存完整時間，
  > 方案二現在才真的可行——本表在那之前寫的「要先確認該表每天都寫得到」講得太輕。

- **解除條件**：[實盤下單架構規劃.md](實盤下單架構規劃.md) Phase5 的盤中事件迴圈上線——
  屆時帳戶會**持續**收到成交回報，本地帳自然帶著當日損益，第三條的缺點消失；
  或是先確認帳戶快照每日可得，改用第二條。

- **做法**：裁示來源後改 `LiveTrader._strategy_loss()` 的取值，其餘不動
  （呼叫端、降級與事件寫入 Phase7-1 都做完了）。

- **產出**：`core/live/trader.py`、`tests/live/test_live_trader_day.py`。

- **驗證方式**：新增一條端到端測試——昨天虧超過 `daily_loss_ratio`，今天開盤段
  不送任何新倉單且 `live_risk_event` 有一筆 `DAILY_LOSS`。

- **相依**：實盤規劃 Phase5（或第二條方案的前置確認）。

> **⏸ 暫緩紀錄（2026-09-20）**
> - 由 Phase7-1 的 ③ 拆出。**接線刻意留著**：判定與降級的路徑是對的，
>   拿掉的話 Phase7-1 等於白做，屆時還要再接一次。
> - `LiveTrader._check_daily_loss()` 的 docstring 已寫明「目前恆為不觸發，
>   缺的是輸入不是接線」，不會有人誤以為這道保護已經生效。

## 已知但本份不做

1. **`core/live/` 沒有重演「基底只宣告骨架」的問題**，不必為它立 Phase4 的對應項。
   實測：`core/live/` 全套件只有 **4 個 `@abstractmethod`**（對照 `core/backtest/report/base.py` 的 13 個），
   且**三個** base class 都是**提供骨架**——`datafeed/base.py` 2 抽象 ＋ 4 具體、
   `notify/base.py` 1 抽象（`deliver`）＋ `send()`／`_guarded_deliver()`／`redact()` 全在骨架
   （所以 `telegram_notifier.py` 只有 70 行）、`datafeed/calendar.py:37` 1 抽象。`oms/`、`risk/`、`report/`、`attribution/` 根本沒有 base class。
   `risk_manager.py` 甚至已經把 6 條純判定抽成模組層函式——**那是正面範例，與 `BaseDataFeed` 同級**。
   唯一的半個例外是 `BaseLiveDataFeed` 缺 DB 生命週期骨架，已列為 Phase7-4。

2. **`MarketCalendar` 的建構形狀未收斂**。`FuturesCalendar` 已經是對的形狀
   （純建構子收交易日清單 ＋ `from_api()` classmethod），`MarketCalendar` 則是一組收 `api` 的 static method。
   兩者收斂後 `core/market/` 可以整個降到 level 2 以下。**沒有現存呼叫端受阻**，
   真要做時以 `FuturesCalendar` 為範本。

3. **`ColumnMapping` 泛型化**。Phase3-1 刻意只做「欄位名集中」不做抽象——
   目前只有台股一個市場，抽象是猜的。等 [美股ETL與回測架構規劃.md](美股ETL與回測架構規劃.md)

   直接 warning 後回空 list，本份維持現狀。

5. **盤中 `close` 語意差異**。Phase3-5 只把它寫成文件與測試註解，**不做修正**——
   那是制度性差異（實盤在收盤前本來就拿不到收盤價），
   屬 [實盤下單架構規劃.md](實盤下單架構規劃.md) Phase4-8 訊號 parity 比對的範疇。

6. **`FuturesBacktestReporter` 的反向繼承**。`FuturesBacktestReporter(StockBacktestReporter)`
   是 refused bequest——三處都在「把繼承來的台股行為關掉」
   （`futures_reporter.py:225` 覆寫 `_get_adjusted_price` 回傳原值、`:74` 寫 `self.price = None`、
   `:69` 註解自承「收下 `price` 只是為了讓兩個 reporter 的建構簽章一致」）。
   正解是把繪圖與權益序列放進 `BaseBacktestReporter`（目前是 13 個抽象方法、0 個實作的空殼），
   讓期貨 reporter 直接繼承它。**但那會改變台股報表圖檔、需重產 baseline**，
   而 `futures_reporter.py:26-33` 的 docstring 已經建議排到美股加入時一起做。**維持該判斷。**
   Phase5-2 先把繪圖抽成 `plotting.py`（純搬家、零行為變更），屆時改繼承只是換注入對象。

7. **`tests/` 根目錄的 73 個扁平測試檔**。見 Phase6-6 的說明，投報比不高。

8. **`LiveReporter` 不算任何績效指標**。`grep -rn "performance_metrics" core/live/` → 0 命中，
   實盤日報沒有 Sharpe／MDD／勝率，無法和回測報表對讀。
   而 `core/backtest/analysis/__init__.py:3-7` 特地說明它是純函式、任何層都可 import。
   建議等 [實盤下單架構規劃.md](實盤下單架構規劃.md) Phase4-8（parity）一起做比較自然，本份不列。

9. **兩條曝險上限的口徑統一**。Phase8-2 只把公式收斂成一份並把差異寫進 docstring，
   **不統一預設值、也不讓回測比照實盤管多單曝險**——後者會改變回測結果、須重產 baseline，
   而且性質上屬於「改變交易邏輯」，與本份範圍界線第 7 點牴觸。真要做時應另立 backlog。
