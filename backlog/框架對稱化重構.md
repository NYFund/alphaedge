# 框架對稱化重構

## Abstract

- **背景／問題**：專案裡有許多「功能相同、結構不同」的成對框架，例如台股與期貨、回測與實盤、各資料類型的 ETL 四件組、各資料表的 API／DAO。
  它們大多是先做一邊、再複製改寫出另一邊，之後各自演進。結果是讀懂一邊不代表看得懂另一邊，而且同一件事在兩邊漂移成不同的行為。
  2026-10-10 以 main（`3242d5e`）全專案盤點 20 組，其中 3 處漂移已經造成**實盤與回測行為不一致**（Phase1-1、Phase1-2）：
  1. 實盤從未呼叫 `enrich_orders()`，SHORT 委託送到券商時會直接拋錯。
  2. 實盤的成本模型不讀策略的設定。
  3. 實盤期貨部位管理沒有注入乘數 resolver。

  這三處目前都還沒觸發：演練只跑 `MomentumStrategy1` 與 `MomentumFuturesStrategy`，兩者都是做多指數或現股。
- **目標**：成對的框架做到「**外框與對外介面一致，只有本質差異各自實作**」，讀一個就看得懂另一個。
  範本是 `台股tick級回測框架.md`〈已定案〉第 8 點：`BarSimulator`／`TickSimulator` 都繼承 `BaseSimulator`，入口都是 `run_day()`，共用的部分放在基底。
- **範圍界線**：**不做**
  1. 不碰 `台股tick級回測框架.md` 涵蓋的檔案與步驟，包括 `core/backtest/backtester.py`、`core/backtest/factory.py`、`core/backtest/simulator/`、逐筆資料源，以及 `core/strategies/base.py` 的 `supported_scales` 與 `live_schedule` 改名。
     與該文件有交集的項目，寫在〈與其他文件的交集〉，交給該文件吸收；若步驟本身動到同一個檔案，就排在該文件的對應步驟之後。
  2. 不碰台股 tick 的 TimescaleDB 程式（`feature/tick-timescaledb`，尚未進 main）。
  3. 不做純改名：理解成本沒有因此下降的名稱一律不動，業界慣例上的偏好也不算理由。
  4. 不把市場本質的差異硬拉成一致，刻意保留的項目列在〈刻意保留的不對稱〉。
  5. 策略作者會碰到的欄位、Enum、鉤子，只列選項（〈待定案〉一），使用者定案前不實作。
- **驗收標準**：
  1. 純重構步驟一律以 `scripts/run_regression.sh` 回歸雙線**零變動**驗收；**結束碼 3（有 skip）不算通過**。worktree 沒有 `data/db/`，必須讓它唯讀讀到主目錄的研究庫，回歸才算真的跑過。
     另外 `pytest -m "not slow"` 要全綠，`check_layer_deps.py`、`check_doc_paths.py` 要通過。
  2. 標了 ⚠ 的步驟會改變回測結果或實盤行為，各自寫明預期變動，回歸差異要逐項解釋並由使用者確認。
  3. 每一組成對框架都能用同一張「方法對照表」描述，兩欄只在本質差異處不同。

> - **`PostgreSQL遷移計畫.md`**：本文件 Phase4-2～Phase4-4 先收斂 DAO 的形狀，該計畫的 Phase2-1、Phase2-2 再改寫 SQL，SQL 只需改寫一次。Phase5-7 與該計畫的 Phase2-2 同段施作。

> - **`core目錄邊界收斂.md` Phase5-1**（`core/pipeline/` 搬到 `etl/`）：Phase5 各步可以在搬家前做，但**不可與搬家放在同一個 commit**，否則 git 的 rename 偵測會失效。
> - **部署時程**：凡是會被實盤 import 的模組，演練期間都不更新主目錄。範圍包括 `core/live/`、`core/broker/`、`core/market/`、`core/position/`、`core/models/`、`core/portfolio/`、`core/datafeed/`。
>   這些步驟可以 merge 進 main，但主目錄的更新排在 `實盤下單架構規劃.md` Phase7-1（模擬環境端到端演練）結束之後；launchd 跑的是主目錄的程式。

## 盤點結果

基準是 main `3242d5e`，日期 2026-10-10，行號以該 commit 為準。「本質」是指市場或資料本身就不同，應該保留；「漂移」是指歷史演進造成的差異，應該收斂。

| # | 組別 | 不對稱的重點 | 判定 | 處理 |

| 1 | 回測 DataFeed 台股↔期貨 | 交易日曆：台股用 `trading_days: Set`，期貨用 `FuturesCalendar`。缺日報告只有台股有；建 DB 目錄只有期貨會做；`close()` 兩邊重複 | 漂移 | Phase3-6 |

## 刻意保留的不對稱

以下差異來自市場或資料本身，收斂反而會把本質藏起來，因此不動。

1. **期貨的結算內容**：逐日結算、換月、到期、以權益判斷追繳；台股則有當沖回補、借券費、除權息、停券與名單檢核。兩邊共用外框（Phase3-3），內容各自實作。
2. **成交規則**：台股有漲跌停、鎖死與 bps 滑價；期貨有跳動點滑價。`StockPriceType` 與 `FuturesPriceType` 的差異（期貨多一個 `MKP`）也屬本質。
3. **權益口徑**：期貨的 `equity` 是 `balance + margin_used`，台股權益由引擎以部位市值計算。只在 docstring 註明兩者不同，不上移到基底。
4. **ROI 分母**：台股用名目價金，期貨用保證金。
5. **盯市的退回值**：台股退回前收；期貨退回 `position.price`，因為逐日結算會重設成本價。
6. **實盤專屬的元件**：`Reconciler`、`MarginGate`、`RiskManager`、`CrossStrategyConflictGuard`、`SessionGuard`。它們處理的是真實券商、非同步成交、多策略共用帳戶，回測沒有對應物。
7. **取報價的方式**：回測的 `get_quotes(date, scale)` 拉歷史，實盤的 `get_live_quotes(timing, symbols)` 拉即時快照；實盤判斷不出交易日時直接拋錯，不猜。
8. **實盤的持倉檔數佔用集合**：實盤把未終結委託也算進去，因為成交是非同步的。`台股tick級回測框架.md` 的 `PendingOrderManager` 上線後，tick 回測會採同一條規則（Phase1-6 提供共用介面）。
9. **實盤停損一律用 `MARKET`**：這是刻意設計，註解已寫明理由。
10. **實盤執行層**（`core/live/execution/`）：股票與期貨已經是對稱的樣板方法結構，不需要調整。
11. **`stock_margin` 與 `futures_margin` 不是同一對東西**：前者是融資融券餘額，後者是交易所保證金，只是名稱撞在一起。資料層不對齊；策略屬性名稱的部分見〈待定案〉Q1。
12. **ETL 的請求單位**：各資料源本來就不同，包括逐日雙市場、逐年區間、月窗、年季加申報期、快照、衍生表與 FinMind 配額。所以**不把所有 `update()` 統一成同一個簽名**（Phase5-6 改用 kwargs builder 吸收差異）。
    期貨連續合約沒有 crawler 也屬本質：它是衍生表。
13. **期貨 quote 的日夜盤整併、期貨沒有還原價**。
14. **保證金查詢用 `effective_date <=`，籌碼查詢用 `<`**：保證金調整當天生效，籌碼則是盤後才公布。

## 待定案

**定案前不開始任何程式碼重構。** 一、二兩節涉及策略作者的介面或回測結果，只列選項；三節是引擎內部命名，有推薦，但仍由使用者選定。

### 一、策略作者會碰到的介面（只列選項，不預設）

**Q1. 期貨策略的資料 API 屬性名稱**（`core/strategies/futures/base.py:100-103`）

- 現況：台股是 `self.price`／`self.chip`／`self.margin`（融資融券），期貨是 `self.futures_price`／`self.margin`（交易所保證金）。同一個 `margin` 在兩邊意思不同，也容易和 `position.margin`、`margin_config` 混淆。`futures_price` 共 218 處／57 檔（含資料層同名識別字）。
- 選項：
  - (a) 維持現狀。
  - (b) 期貨的 `futures_price` 改成 `price`，型別標註成 `FuturesPriceAPI`，兩邊對稱。
  - (c) 只把期貨的 `margin` 改成 `margin_api`（或 `margin_table`）。
  - (d) (b)＋(c)。
- 另一個子問題：`FuturesChipAPI` 目前沒有接進期貨的 DataFeed 與策略基底。要不要接？

**Q2. `setup_account()` 樣板**

- 現況：三層基底都把它宣告成 abstract，6 支具體策略的實作都只有 `self.account = account`。共 52 處／28 檔。
- 選項：
  - (a) 基底提供預設實作，子類可覆寫。
  - (b) 移除這個鉤子，由引擎直接設定 `strategy.account`（Zipline 的 `context`、LEAN 的 `Portfolio` 都由引擎注入）。
  - (c) 維持現狀。

**Q3. 期貨的部位大小與 `calculate_max_lots()` 死鉤子**

- 現況：
  - 台股用可插拔的 `self.sizer`，期貨用 `max_lots`／`max_capital_usage`，演算法寫死在 `FuturesPortfolioConstructor` 裡。
  - `BaseFuturesStrategy.calculate_max_lots()`（`futures/base.py:194`）的 docstring 說它是可覆寫的鉤子，但 constructor 呼叫的是自己的 `calculate_max_lots`（`construction.py:163`），所以策略覆寫了也不會生效。
- 選項：
  - (a) 新增 `MarginSizer(BasePositionSizer)`，期貨也改用 `self.sizer`，`max_lots`／`max_capital_usage` 變成 sizer 的參數（Backtrader `Sizer`、LEAN `PortfolioConstructionModel`）。
  - (b) 保留欄位，只讓 constructor 回呼策略的鉤子，使鉤子真的生效。
  - (c) 保留欄位，刪掉策略上的 `calculate_max_lots`／`get_margin_per_lot`。
  - (d) 維持現狀。
- 子問題：sizing 要不要也把開倉手續費與稅算進去？PM 開倉檢查的是「保證金＋手續費＋稅」（`calculate_opening_requirement`），sizing 只算保證金。算進去的話，邊界口數可能少 1 口，**會改變回測結果**。

**Q4. 部位的進場價**

- 現況：期貨的 `position.price` 每天會被逐日結算重設，所以另有 `entry_price`；台股沒有這個欄位。
- 選項：
  - (a) 在 `BasePosition` 新增不可變的 `entry_price`，純新增。
  - (b) 期貨會變動的 `price` 改名為 `mark_price` 或 `settlement_price`。這是破壞性改動。
  - (c) 維持現狀。

**Q5. `margin_call_policy` 放在哪裡**

- 現況：台股是策略欄位（`stock/base.py:61`），由 factory 傳進 settlement；期貨則放在 `FuturesMarginConfig.margin_call_policy`。
- 選項：
  - (a) 兩邊都改成策略欄位。
  - (b) 兩邊都放進市場的設定物件（台股新增對應的設定物件）。
  - (c) 維持現狀。

**Q6. 平倉與停損鉤子收到的報價範圍**

- 現況：
  - 回測只給有持倉的標的（`backtester.py:510`、`:546`）。
  - 實盤給「標的池＋持倉」的全部報價（`feature/post-rehearsal` 的 `quote_symbols()`）。
  - 實盤兩個鉤子在同一份狀態上一起算，沒有扣掉在途的停損單，同一部位可能同時送出停損與平倉兩張單；回測則是停損成交後重掃剩餘部位。
  - 現有四支策略都自己再過濾一次持倉，所以還沒出事。
- 選項：
  - (a) 實盤改成只給有持倉的報價，與回測契約一致。
  - (b) 回測改成也給全部報價；這要由 `台股tick級回測框架.md` 處理。
  - (c) 契約寫明「可能收到非持倉標的」，維持兩邊現狀。
- 子問題：實盤要不要在呼叫平倉鉤子前，先扣掉已有在途停損單的部位？

**Q7. 月營收與財報的 `get_range` 參數順序**

- 現況：`MonthlyRevenueReportAPI.get_range(sy, ey, sm, em)` 的順序和 DAO 的 `(sy, sm, ey, em)` 相反，財報也一樣。用位置參數傳錯不會報錯，只會靜默查錯區間。`core/strategies/README.md` 有教策略作者呼叫它。
- 選項：
  - (a) 改成 keyword-only（`*,`）。
  - (b) API 改成與 DAO 同序。
  - (c) 改收 `(year, month)` tuple。

**Q8. 價格序列的回傳型別**

- 現況：`StockPriceAPI.get_close_series` 的 index 是字串、Series 帶 name；`FuturesPriceAPI` 的 index 是字串、沒有 name；`FuturesContinuousAPI` 的 index 是 `datetime.date`、值轉成 float。`reporter.py:94` 只好自己補一行轉換。
- 選項：
  - (a) 統一為 index `datetime.date`、dtype float、name 為「收盤價」。
  - (b) 統一為 index 字串。
  - (c) 維持現狀，只在 docstring 註明。
- 現有呼叫端都用 `iloc`，選 (a) 或 (b) 回測結果都不變。

### 二、會改變回測結果或實盤行為的裁示

**Q9. 盤後才公布的資料，在回測裡何時可以用**（Phase4-6）

- 選項：
  - (a) 融券檢核改用 T−1，並在 `BaseDataAPI` 宣告每個資料集的公布時點，盤後資料一律提供 `get_available(date)`。
  - (b) 只把融券檢核改用 T−1。
  - (c) 維持現狀，在文件中註明。
- 選 (a) 或 (b) **會改變 SHORT 線的回測結果**，需要重產 baseline。融券餘額這一處動的是 `backtester.py`，要和 `台股tick級回測框架.md` Phase1-4 協調。

**Q10. 期貨無成交的合約**（Phase3-1）

- 期貨 cleaner 把 `-` 轉成 NULL。讀出來是 NaN 時，區間檢查會拒單；讀出來是 None 時，**任何價格都會成交**。adapter 也會產出 `close` 為 NaN 的 quote。
- 先實測，再決定：
  - (a) 期貨補上與台股相同的無成交日擋板。
  - (b) 無成交合約改用 `settlement_price` 盯市。
  - (c) (a)＋(b)。
  - (d) 實測確認一定拒單時，維持現狀。

**Q11. 期貨的無報價門檻與事件 key**（Phase3-3）

- 期貨門檻是類別常數 3，不能調；台股是策略欄位，預設關閉。
- 選項：
  - (a) 期貨也開放策略設定，預設 3。
  - (b) 維持常數。
- 事件 key：期貨多單現在記成 `forced_cover_no_quote`，台股多單記成 `forced_exit_no_quote`。要不要統一？統一的話期貨事件報表的計數會變，PnL 不變。

**Q12. 兩支語意不同的 `get_contract_size`**

- `FuturesMarginAPI`（`:202`）用 `per_product=True`，`FuturesStockUniverseAPI`（`:113`）用 `per_product=False`。同一個 (product, date) 用來算保證金的契約單位，可能和算損益的乘數不同；註解說這是刻意的。
- 選項：
  - (a) 保證金端改名為 `get_margin_contract_size`，把差異寫在名字上。
  - (b) 兩邊共用同一個解析，**可能改變股期的保證金數字**。
  - (c) 維持現狀。

**Q13. 期貨 sizing 是否計入開倉成本**：見 Q3 的子問題。

**Q14. ETL 來源失聯時的結束碼**（Phase5-5）

- 財報三張報表的 crawler 失敗時回傳 None，updater 就跳過；站方全面失聯時 `fs` target 仍以結束碼 0 收場。
- 改成一律回傳 `CrawlResult` 之後，原本靜默成功的 target 會變紅。`update_db` 由 launchd 每天排程執行，結束碼變了，告警也會跟著出現。
- 選項：
  - (a) 一律改。
  - (b) 只改財報。
  - (c) 維持現狀。

- **驗證方式**：手寫 SHORT 開倉與回補委託，經 `_preprocess()` 後都帶 `short_method`；`allow_day_trade=True` 的 SHORT 部位 `is_day_trade` 為真，`uncovered_day_trade_positions()` 會回傳它；回歸雙線零變動。

### Phase2-1. ⚠ 期貨保證金只留一份查表（`FuturesMarginModel`） ⬜

  回測零變動，期貨多一行缺日 log。
- **產出**：`core/datafeed/base.py`、`core/backtest/datafeed/tw/` 兩檔與測試。

### Phase5-1. ETL：除權息與減資兩支雙胞胎 updater 共用基底 ⬜

- **目的**：`StockDividendUpdater.update()` 與 `CorporateActionUpdater.update()` 約 90 行逐行相同，都是逐年區間、雙市場、`ColumnLayoutError` 隔離、`CleanFailureError`、先入庫再拋。差別只有三處：

### Phase5-2. ETL：節流與中止收斂成一種寫法 ⬜

- **目的**：

### Phase5-5. ⚠ ETL：crawler 一律回傳 `CrawlResult` ⬜

- **目的**：crawler 的回傳分兩族：
  - 三態的 `CrawlResult`：行情、籌碼、融資融券、名單、除權息、減資、月營收、休市日、期貨行情。
  - `Optional[...]`：財報、期貨籌碼、期貨保證金、股期清單、FinMind、tick。
  後者把「查無資料」和「沒問到」混成 None。財報這條路徑又沒有 `UpdateStats` 與 `raise_if_unreachable`，站方全面失聯時仍以結束碼 0 收場。
- **做法**：依〈待定案〉Q14 的範圍，改成回傳 `CrawlResult`，優先處理財報。期貨籌碼把「None 而且有交易日」對應成 `FAILED`，保留本質判準。
- **影響**：財報 4 個、期貨籌碼 3 個、期貨保證金 4 個、股期清單 1 個、FinMind 4 個 crawl 方法。資料內容不變，**target 的成敗與結束碼會改變**。
- **產出**：上列檔案與測試。
- **驗證方式**：模擬站方失聯時 target 以非零結束碼收場；正常時寫入資料不變。
- **相依**：〈待定案〉Q14。`update_db` 由 launchd 排程執行，主目錄的更新排在演練結束之後。

### Phase5-6. ETL：updater 生命週期一致，`update_db` 改為表格驅動 ⬜

- **目的**：
  - 收尾方法不一致：18 支 updater 中 11 支有 `close()`，stock tick 用 `cleanup()`，期貨 tick 用 `logout()`。`BaseDataUpdater` 沒有定義生命週期，`update_db` 只能逐支手寫 `try/finally`。
  - `update_db` 的 `main()` 有 23 個幾乎一樣的區塊。
  - `LogManager.setup_logger` 在 13 處各寫一次。
- **做法**：
  - `BaseDataUpdater` 提供 `LOG_FILE_NAME`（由 `setup()` 統一呼叫）、預設的 `close()`、`__enter__`／`__exit__`。
  - `update_db` 改成 target 註冊表：`TARGETS: Dict[str, TargetSpec]`，欄位是 factory、kwargs builder、`explicit_only`、`needs_tick`，23 個區塊收斂成一個迴圈。
  - **不**把所有 `update()` 統一成同一個簽名，差異由 kwargs builder 吸收（見〈刻意保留的不對稱〉第 12 點）。
- **影響**：18 支 updater 與 `apps/update_db.py`。各 target 行為不變。
- **產出**：上列檔案與測試。
- **驗證方式**：每個 target 以 `--dry-run` 或暫存 DB 跑一次，行為與改動前相同。
- **相依**：`feature/tick-timescaledb` merge。它把 `tasks/update_db.py` 搬到 `apps/`、重寫了 `stock_tick_updater.py`、刪掉期貨 tick 四件組；不等它合併一定衝突。

### Phase5-7. ETL：loader 拆成兩種契約 ⬜

- **目的**：`BaseDataLoader.add_to_db(*args, **kwargs)` 底下有兩族互不相容的簽名：
  - CSV 重放型：`(remove_files, only_dates)`。
  - DataFrame 型：`(df[, table|year]) -> int`。

- **做法**：
  - 拆成 `CsvReplayLoader.add_to_db(remove_files, only_dates)` 與 `FrameLoader.load_frame(df, **key) -> int`，舊名先留作別名。
  - 移除 `crawl()` 的 abstract 標記與空殼。
  - CSV 一律由 cleaner 落地。
- **影響**：各 loader。寫入資料不變。
- **產出**：上列檔案與測試。
- **驗證方式**：各 loader 以暫存 DB 寫入，結果與改動前逐列相同。
- **相依**：與 `PostgreSQL遷移計畫.md` Phase2-2 同段施作。該步驟要清掉 DAO 之外的 `conn.commit()`，名單正好包含期貨籌碼、財報、FinMind 的 loader，不要各改一次。

### Phase5-8. ⚠ ETL：期貨行情與籌碼的日期規劃改走 `DatePlanner` ⬜

- **目的**：日期規劃有四套。期貨行情每個商品用 `MAX(date)+1` 再補 `find_gap_dates`（`futures_price_updater.py:126`、`:213`、`:255`），這正是 `date_planner.py` 的模組說明明文禁止的作法，只是事後再補洞；期貨籌碼也是每張表 `MAX+1` 再補洞。
- **做法**：提供逐商品的 DAO 轉接器，`calendar_dates` 用現貨交易日，週末補行日放進 `extra_dates`。期貨行情「只有夜盤時整天不入庫」與「保險絲從區間開頭起算」兩條本質規則要保留。
- **影響**：**可能改變寫入的資料**：候選集合從「`MAX+1` 加缺口」變成真正的差集，可能多補到資料；2013 年前缺現貨日曆那一段的行為要重新確認。
- **產出**：上列檔案與測試。
- **驗證方式**：先輸出新舊兩版的候選日期集合做 diff，差異逐項解釋後才實際寫入。
- **相依**：Phase5-4、Phase5-6。整合成本最高，排在 Phase5 最後。
