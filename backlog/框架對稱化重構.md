# 框架對稱化重構

## Abstract

- **背景／問題**：專案裡有許多「功能相同、結構不同」的成對框架，例如台股與期貨、回測與實盤、各資料類型的 ETL 四件組、各資料表的 API／DAO。
  它們大多是先做一邊、再複製改寫出另一邊，之後各自演進。結果是讀懂一邊不代表看得懂另一邊，而且同一件事在兩邊漂移成不同的行為。
  2026-10-10 以 main（`3242d5e`）全專案盤點 20 組，其中 3 處漂移已經造成**實盤與回測行為不一致**（Phase1-1、Phase1-2，皆已修正）：
  1. 實盤從未呼叫 `enrich_orders()`，SHORT 委託送到券商時會直接拋錯。
  2. 實盤的成本模型不讀策略的設定。
  3. 實盤期貨部位管理沒有注入乘數 resolver。
- **目標**：成對的框架做到「**外框與對外介面一致，只有本質差異各自實作**」，讀一個就看得懂另一個。
  範本是 `台股tick級回測框架.md`〈已定案〉第 8 點：`BarSimulator`／`TickSimulator` 都繼承 `BaseSimulator`，入口都是 `run_day()`，共用的部分放在基底。
- **現況（2026-10-18）**：36 項完成 31 項，全部在 `feature/framework-symmetry`（以 `feature/tick-backtest` 為底，含 post-rehearsal、tick-timescaledb 的程式），**2026-10-27 隨 `2026-10里程碑收尾排程.md` S19 部署進 main（`14037bf1`）**；
  依合併順序 post-rehearsal → tick-timescaledb → tick-backtest → framework-symmetry 合入，五次皆無衝突。
  剩下 5 項（Phase2-2 於 2026-10-18 完成）：Phase1-6～Phase1-8（卡在 `重構後全專案健檢.md` Phase7-1 拆 `trader.py`）、Phase2-6 的改名（前提「三個上游分支進 main」已於 2026-10-27 成立，可排工）、Phase5-7（與 `PostgreSQL遷移計畫.md` Phase2-2 同段）。
- **範圍界線**：**不做**
  1. 不重做 `台股tick級回測框架.md` 已完成的內容（16／16 項 2026-10-11 完成，在 `feature/tick-backtest`）。
     該文件已無未完成步驟，原本規劃「由它吸收」的回測端改動（Phase1-6 的 `BaseSimulator` 接線、Phase2-2 的 `backtester.py` 呼叫點）**改由本文件自己做**，見各步驟。
  2. 不碰台股 tick 的 TimescaleDB 程式本身（`feature/tick-timescaledb`）。
  3. 不做純改名：理解成本沒有因此下降的名稱一律不動，業界慣例上的偏好也不算理由。
  4. 不把市場本質的差異硬拉成一致，刻意保留的項目列在〈刻意保留的不對稱〉。
  5. 策略作者會碰到的欄位、Enum、鉤子，只列選項（〈待定案〉一），使用者定案前不實作。
- **驗收標準**：
  1. 純重構步驟一律以 `scripts/run_regression.sh` 回歸雙線**零變動**驗收；**結束碼 3（有 skip）不算通過**。worktree 沒有 `data/db/`，必須讓它唯讀讀到主目錄的研究庫，回歸才算真的跑過。
     另外 `pytest -m "not slow"` 要全綠，`check_layer_deps.py`、`check_doc_paths.py` 要通過。
  2. 標了 ⚠ 的步驟會改變回測結果或實盤行為，各自寫明預期變動，回歸差異要逐項解釋並由使用者確認。
  3. 每一組成對框架都能用同一張「方法對照表」描述，兩欄只在本質差異處不同。

>   本分支已完成的 Phase1～Phase3 多數落在這個範圍，隨分支在 `實盤下單架構規劃.md` Phase7-1 演練結束後進 main；launchd 跑的是主目錄的程式。

## 刻意保留的不對稱

以下差異來自市場或資料本身，收斂反而會把本質藏起來，因此不動。

1. **期貨的結算內容**：逐日結算、換月、到期、以權益判斷追繳；台股則有當沖回補、借券費、除權息、停券與名單檢核。兩邊共用外框（Phase3-3），內容各自實作。
2. **成交規則**：台股有漲跌停、鎖死與 bps 滑價；期貨有跳動點滑價。`StockPriceType` 與 `FuturesPriceType` 的差異（期貨多一個 `MKP`）也屬本質。
3. **權益口徑**：期貨的 `equity` 是 `balance + margin_used`，台股權益由引擎以部位市值計算。只在 docstring 註明兩者不同，不上移到基底。
4. **ROI 分母**：台股用名目價金，期貨用保證金。
5. **盯市的退回值**：台股退回前收；期貨退回 `position.price`，因為逐日結算會重設成本價。
6. **實盤專屬的元件**：`Reconciler`、`MarginGate`、`RiskManager`、`CrossStrategyConflictGuard`、`SessionGuard`。它們處理的是真實券商、非同步成交、多策略共用帳戶，回測沒有對應物。
7. **取報價的方式**：回測的 `get_quotes(date, scale)` 拉歷史，實盤的 `get_live_quotes(timing, symbols)` 拉即時快照；實盤判斷不出交易日時直接拋錯，不猜。
8. **實盤的持倉檔數佔用集合**：實盤把未終結委託也算進去，因為成交是非同步的。逐筆回測（`TickSimulator.check_max_holdings()`）已採同一條規則：部位 ∪ `PendingOrderManager` 的在途開倉；日 K 回測只看部位。Phase1-6 由呼叫端傳入佔用集合，不統一這一點。
9. **實盤停損一律用 `MARKET`**：這是刻意設計，註解已寫明理由。
10. **實盤執行層**（`core/live/execution/`）：股票與期貨已經是對稱的樣板方法結構，不需要調整。
11. **`stock_margin` 與 `futures_margin` 不是同一對東西**：前者是融資融券餘額，後者是交易所保證金，只是名稱撞在一起。資料層不對齊；策略屬性名稱的部分見〈待定案〉Q1。
12. **ETL 的請求單位**：各資料源本來就不同，包括逐日雙市場、逐年區間、月窗、年季加申報期、快照、衍生表與 FinMind 配額。所以**不把所有 `update()` 統一成同一個簽名**（Phase5-6 改用 kwargs builder 吸收差異）。
    期貨連續合約沒有 crawler 也屬本質：它是衍生表。
13. **期貨 quote 的日夜盤整併、期貨沒有還原價**。
14. **保證金查詢用 `effective_date <=`，籌碼查詢用 `<`**：保證金調整當天生效，籌碼則是盤後才公布。

### Phase3-1. ⚠ 實測期貨無成交日能否成交，再決定是否補擋板 ✅

- **目的**：台股 `validate()` 以 `has_tradable_quote()` 擋掉無成交日，期貨沒有這道擋板；期貨 cleaner 把 `-` 轉成 NULL，讀出來可能是 NaN 或 None。

**實測紀錄（2026-10-11，main `67ff3b5`，`tw_futures.db` 2026-10-08 的複本，唯讀）**

- 資料面：`futures_price_daily` 141,941 列，收盤價 NULL 的 45,019 列全是成交量 0；另有 614 列只成交一筆、高低價為 NULL。pandas 讀 SQLite 時一欄有任何數字就是 float64（NULL 成 NaN），整欄 NULL 才是 object（NULL 成 None），所以讀值取決於同一次查詢的其他列。

| 型態 | 範例 | 報價讀值 | `validate()`（開倉腿） |
|------|------|----------|------------------------|
| 零成交，同查詢有其他成交列 | 2026-08-25 TX202706 日盤 | OHLC 為 NaN；結算價 46,392 | 任何價格都拒單，計入 `rejected_fill_price` |
| 只成交一筆，高低價 NULL | 2026-08-26 TX202703 日盤，收盤 45,806 | close 有值；high／low 為 NaN | **委託價等於收盤價也拒單**（誤拒） |
| 該商品該時段當天全部零成交 | 2026-10-01 TF 夜盤（TF 夜盤 5 天、ZFF 夜盤 1 天） | OHLC 與結算價全為 None | **任何價格都通過** |

- 其他路徑：平倉腿不經 `validate()`，區間為 NaN／None 時放行並以 NaN 成交；夜盤沒有結算價，零成交時盯市價變 NaN、權益全變 NaN，且 NaN 被當成「有報價」；日夜盤整併把夜盤 NaN 當成有成交，日盤開盤價被覆寫成 NaN（1,431 列）。
- 對現行策略：TX、MTX、TMF 的近月與次月沒有任何 NULL 列，**當時的回測結果與 baseline 都沒有受影響**；受影響的是 TE／TF／ZEF／ZFF 與遠月。

**修正紀錄（2026-10-12，`feature/framework-symmetry`，依〈待定案〉Q10 (c)）**

| 實測的問題 | 修正 | 位置 |
|------|------|------|
| NaN／None 兩種表示法 | `to_price()`：價格欄位的 NULL／NaN 一律轉成 **0.0**（`BaseQuote` 價格欄位是 `float`，0 是既定的「沒有這個價」）；結算價與未沖銷契約量維持 None | `FuturesQuoteAdapter.from_day_row()` |
| 整組 None 時任何價格都成交 | `has_tradable_quote()` 擋板搬到 `BaseFillModel`，期貨也走 | `fill_model.py` |
| 單筆成交被誤拒 | `get_price_range()` 在高低價缺、收盤價有值時回 `[close, close]` | `fill_model.py` |
| 平倉腿以 NaN 成交 | `filter_tradable_quotes()`：策略的三個鉤子只收到有成交的報價；零成交契約的開倉單走 `rejected_no_quote`，平倉留給結算層的連續無報價出場 | `BaseSimulator` |
| 夜盤零成交盯市變 NaN | 價格統一成 0 後，日盤零成交以結算價盯市、夜盤沿用 `position.price`；`update_no_quote_days()` 改以「有盯市價」為有報價 | `tw_futures.py` |
| 整併把夜盤 NaN 當成有成交 | 統一成 0 後 `combine_quote()` 的判斷生效 | `futures_quote_adapter.py` |
| 轉倉轉進零成交的新契約（修正時發現） | `roll_positions()` 的判斷對 0 生效，不轉倉 | `tw_futures.py` |

- 順帶的語意變化：`select_near_month()` 的候選只剩有成交的契約；當家契約當天零成交時會退到最近的有成交到期月。現行策略的 TX／MTX／TMF 近月不受影響。

### Phase5-7. ETL：loader 拆成兩種契約 ⬜

- **目的**：`BaseDataLoader.add_to_db(*args, **kwargs)` 底下有兩族互不相容的簽名：
  - CSV 重放型：`(remove_files, only_dates)`。
  - DataFrame 型：`(df[, table|year]) -> int`。
  另外，`BaseDataCrawler.crawl()` 是 abstract、多數 crawler 只放空殼，`BaseDataCleaner` 沒有 `clean` 契約。CSV 由誰落地也不一致：多數由 cleaner 寫，期貨籌碼與連續合約由 updater 呼叫 `loader.save_csv`。
- **現況（2026-10-18 實查 `feature/framework-symmetry`）**：與上述相符——`add_to_db` 在 17 支 loader 各有一份；`save_csv` 由 updater 呼叫的仍是 `futures_chip_updater.py`、`futures_continuous_updater.py` 兩處；`base_crawler.py` 的 `crawl()` 仍為 abstract。處數實作時再量。
- **做法**：
  - 拆成 `CsvReplayLoader.add_to_db(remove_files, only_dates)` 與 `FrameLoader.load_frame(df, **key) -> int`，舊名先留作別名。
  - 移除 `crawl()` 的 abstract 標記與空殼。
  - CSV 一律由 cleaner 落地。
- **影響**：各 loader。寫入資料不變。
- **產出**：`core/pipeline/shared/{base_loader,base_crawler,base_cleaner}.py`、各 loader、期貨籌碼與連續合約 updater、測試。
- **驗證方式**：各 loader 以暫存 DB 寫入，結果與改動前逐列相同。
- **相依**：與 `PostgreSQL遷移計畫.md` Phase2-2（⬜，相依其 Phase2-1）同段施作。該步驟要清掉 DAO 之外的 `conn.commit()`，名單正好包含期貨籌碼、財報、FinMind 的 loader，不要各改一次。
  不可與 `core目錄邊界收斂.md` Phase5-1（`core/pipeline/` 搬到 `etl/`，⏸）放在同一個 commit。
