# 策略分層重構（Alpha／Portfolio 分離）

## Abstract

- **背景／問題**：策略的「選標的」與「決定部位大小」兩件事**混在同一個方法裡**，層次邊界只是約定，引擎看不見也強制不了。
  - `MomentumStrategy1.check_open_signal()` 前段是篩選（Alpha），最後一行 `return self.calculate_position_size(...)` 是部位計算（Portfolio Construction）——**兩層之間只隔一行**。
  - `Backtester` **只呼叫** `check_open_signal`／`check_close_signal`／`check_stop_loss_signal` 三個鉤子（`backtester.py` 的 518、612、645 行）；`calculate_position_size()` 是策略內部自己串的，雖然掛著 `@abstractmethod`，**但它不是引擎契約**。
  - `BaseStockStrategy` 匯入 `from core.backtest.models.sizing import ...`：**實盤執行時，策略層會 import `core.backtest.*`**。部位大小不是回測概念（回測與實盤共用），放在 `backtest/models/` 底下是分層錯置。
  - `max_holdings` 被檢查**兩次**：`EqualWeightSizer.size()` 一次、`Backtester.check_max_holdings()` 一次。
  - 期貨基底完全不用 `sizer`，走 `calculate_max_lots()`（保證金約束）——同一層已經有兩種實作，卻沒有共同介面。
- **目標**：讓分層由**型別與目錄**承載，而不是靠約定。
  - 新增 `core/portfolio/`：`Signal` 模型、部位大小（由 `core/backtest/models/sizing.py` 搬入）、`Signal → Order` 的組裝。
  - 策略類別內部拆成兩段：`generate_*_signals()` 回傳 `List[Signal]`（Alpha），`check_*_signal()` 由基底提供、負責呼叫 portfolio 層（策略不再自行實作）。
  - **引擎對策略的契約完全不變**：`check_*_signal(quotes) -> List[Order]`，`Backtester` 與 `LiveTrader` 一行都不用改。
- **範圍界線（不做）**：
  - **不改 `Backtester` 對策略的呼叫契約**，也不改引擎的任何撮合邏輯。
  - **不改任何策略的交易邏輯**：篩選條件、參考價、張數公式全部原樣搬移。
  - 不把 `BasePositionSizer` 改名。它本來就是 portfolio 層，換名字只有 churn、沒有功能。
  - **不為「只有一個實作」的層建抽象基底**：不做 `AlphaModel`、`RiskModel` 這類形式化介面。抽象的價值是可替換，只有一個實作時那層不會被行使，只剩間接性的代價。
  - 不動 `core/live/risk/`——風控層是[實盤下單架構規劃.md](實盤下單架構規劃.md) Phase3-3 的範圍，本文件不重複。
  - 不做多策略組合回測（依實盤文件〈多策略〉§7，要等 Phase7-1 的數據才決定做不做）。
- **驗收標準**：
  1. `./scripts/run_regression.sh` **零變動**，baseline 沒有重產。
  2. 三支既有策略（`MomentumStrategy1`、`ForeignSellShortDayTradeStrategy`、`MomentumFuturesStrategy`）都只實作 `generate_*_signals()`，`check_*_signal()` 一律由基底提供。
  3. `grep -rn "core.backtest.models.sizing" core/` 無結果：策略層不再為了「部位大小」而依賴回測層。
     - **已知限制（刻意不做）**：`core/strategies/` 仍會 import `core.backtest` 的 `BaseDataFeed`、
       `CostConfig`／`FuturesCostConfig`、`FillConfig`／`FuturesFillConfig`、`MarketCalendar`、
       `FuturesCalendar`、`FuturesRollConfig`——2026-09-19 實測共 **6 個檔、13 處**。那是同一種
       分層錯置，但搬動它們會牽動 DataFeed 與成本／成交模型的所有呼叫端，影響面遠大於 `sizing`，
       **不在本文件範圍**。[實盤下單架構規劃.md](實盤下單架構規劃.md) Phase0-4 對 `BaseDataFeed`
       已有相同裁示（「把 `BaseDataFeed` 移到中立位置不在本文件範圍」），本文件沿用同一條界線。
  4. `python scripts/check_layer_deps.py` 通過，且 `core/portfolio/` 已登記分層。
  5. `pytest` 全部通過。

## 目標分層

```
core/
├── strategies/          ① Alpha           選標的、定方向 → List[Signal]
├── portfolio/           ② Portfolio       Signal + Account → List[Order]
│   ├── signal.py            Signal 模型
│   ├── sizing.py            部位大小（← 由 core/backtest/models/ 搬入）
│   ├── construction.py      Signal → Order 的組裝（策略內）
│   └── aggregation.py       跨策略：資金分配、同標的仲裁（判定，純函式）※ 由實盤文件 Phase3-8／3-9 實作
├── execution/           ③ 委託前處理       方向白名單、排序（實盤文件 Phase3-4）
├── live/risk/           ④ Risk            PreTradeRiskManager（實盤文件 Phase3-3，本文件不做）
└── live/oms/＋broker/   ⑤ Execution       送單；回測側對應 backtest/models/fill_model.py
```

### 命名原則

**分層要看得見，靠的是型別與目錄，不是命名。** 但在語意真的對得上的地方，一律採業界通稱，
讓日後查資料、與人討論時不必翻譯：

| 本專案 | 業界術語 | 說明 |
|--------|----------|------|
| `core/portfolio/` | portfolio construction | 決定「持有什麼、多少」 |
| `generate_*_signals()` | signal generation | Alpha 層的標準動詞，與 `Signal` 型別成對 |
| `BasePortfolioConstructor` | portfolio construction model | 不用 `Builder`——那是 GoF 設計模式名，會混淆 |
| `aggregation.py` | portfolio aggregation | 把多個 **sleeve**（帳戶內由單一策略管理的子組合）的部位合成帳戶層 |
| `BasePositionSizer` | position sizing | 既有命名已是標準詞，不動 |
| `PreTradeRiskManager` | pre-trade risk | 見下方「不採用」第 2 點 |

**刻意不採用的兩個業界名稱**（抄名字的前提是語意真的一樣，否則是把系統沒有的東西寫進名字裡）：

1. **`PortfolioTarget`**（LEAN）：它隱含「宣告目標權重、引擎自行計算差額」的再平衡語意。
   本專案的策略直接產生訂單，沒有 target-weight 機制，用這個名字會誤導。
2. **`RiskModel`**：在「事前風控」與「因子風險模型」之間有歧義，兩者是完全不同的東西。
   既有的 `PreTradeRiskManager` 比業界通稱精準，保留。

## 步驟詳述

### S1. 建立 `core/portfolio/`，`sizing.py` 搬家 ⬜

- **目的**：部位大小是回測與實盤**共用**的邏輯，不該放在 `core/backtest/` 底下。現況是策略層在實盤執行時會 import `core.backtest.*`，方向相反。
- **做法**：
  - 新增 `core/portfolio/__init__.py`，把 `core/backtest/models/sizing.py` 整檔搬到 `core/portfolio/sizing.py`，**內容一字不改**。
  - 改 import 點（實測只有 2 處）：
    - `core/strategies/stock/base.py:13`
    - `tests/backtest/test_position_sizer.py:6`（測試一併移到 `tests/portfolio/test_position_sizer.py`）
  - `scripts/check_layer_deps.py` 的 `_LAYER_RULES` 新增 `("core.portfolio", 4, "部位建構層", False)`：只可 import `core.models`／`core.utils`，**不可 import `core.backtest`／`core.live`／`core.strategies`**。
- **產出**：見進度追蹤表。
- **驗證方式**：`pytest`；`check_layer_deps.py` 通過；`./scripts/run_regression.sh` 零變動（純搬家，本來就該零變動）。
- **相依**：無。可以最先做。

### S2. `Signal` 模型 ⬜

- **目的**：讓 Alpha 層的輸出有明確型別。現在策略是把 `List[StockQuote]` 直接丟給 `calculate_position_size()`，外加一個 `action` 參數——**報價不是訊號**，它沒有方向也沒有強度，層次邊界因此表達不出來。
- **做法**：
  - `core/portfolio/signal.py` 定義 `Signal`：
    - `symbol: str`、`quote: BaseQuote`（產生本訊號的報價）
    - `action: Action`、`position_type: PositionType`
    - `reference_price: float`：**該策略選定的參考價**。現行三支策略分別用 `close`／`open`／`tick_quote.close`，這是策略決策，不可由 portfolio 層代選（`sizing.py` 的模組說明已載明這條責任邊界，本欄位是它的具體化）。
    - `strength: Optional[float] = None`：訊號強度。**現階段沒有任何策略使用**，一律 `None`；它的用途是日後換波動度加權／conviction 加權時，portfolio 層才有輸入可用。沒有這個欄位，換配置演算法就得同時改 Alpha 層。
  - 依 `CLAUDE.md` §2.4 標註所有型別；`Optional[T]` 欄位在 `__init__` 給預設值 `None`。
- **產出**：`core/portfolio/signal.py`。
- **驗證方式**：單元測試；`Signal` 不 import 任何引擎模組（`check_layer_deps.py` 涵蓋）。
- **相依**：S1。

### S3. `BasePortfolioConstructor` 與兩個實作 ⬜

- **目的**：把「`List[Signal]` → `List[Order]`」這段組裝從各策略的 `calculate_position_size()` 收成共用實作。
- **做法**：
  - `core/portfolio/construction.py`：
    - `BasePortfolioConstructor.build(signals, account) -> List[BaseOrder]`（抽象）。
    - `StockPortfolioConstructor`：呼叫 `self.sizer.size(account, [(quote, reference_price), ...], max_holdings)`，再把回傳的張數組成 `StockOrder`。**公式與取整規則原樣沿用 `EqualWeightSizer`，不做任何調整。**
    - `FuturesPortfolioConstructor`：走保證金約束（`calculate_max_lots()` 的邏輯），**不是資金切分**。股票「用多少錢買多少股」、期貨「繳多少保證金開幾口」，兩者不可共用同一個公式。
  - **這一層有兩個實作，所以介面有意義**——這是本文件唯一新增的抽象基底，其餘各層一律不加。
- **產出**：`core/portfolio/construction.py`。
- **驗證方式**：以三支既有策略的實際輸入餵進去，輸出的張數／口數與改寫前**逐筆相同**。
- **相依**：S2。

### S4. `BaseStrategy` 分層鉤子 ⬜

- **目的**：讓 Alpha 與 Portfolio 在策略類別裡由**不同方法**承載，且策略作者不必自己串。
- **做法**：
  - `BaseStrategy` 新增三個抽象鉤子（Alpha 層，策略**只需要**實作這些）：
    - `generate_open_signals(quotes) -> List[Signal]`
    - `generate_close_signals(quotes) -> List[Signal]`
    - `generate_stop_loss_signals(quotes) -> List[Signal]`
  - `check_*_signal()` **下沉到基底**，不再是抽象方法：

    ```python
    def check_open_signal(self, quotes: List[BaseQuote]) -> List[BaseOrder]:
        """開倉：Alpha 選出候選後交由 portfolio 層換算部位"""

        signals: List[Signal] = self.generate_open_signals(quotes)
        return self.portfolio_constructor.build(signals, self.account)
    ```

  - `calculate_position_size()` 解除 `@abstractmethod`，保留為可覆寫的鉤子（要客製組裝的策略仍可覆寫），**但預設不再需要每支策略自己寫**。
  - `self.portfolio_constructor: BasePortfolioConstructor` 在 `BaseStockStrategy`／`BaseFuturesStrategy` 各自給預設值，與 `self.sizer` 的既有做法一致。
- **產出**：`core/strategies/base.py`、`core/strategies/stock/base.py`、`core/strategies/futures/base.py`。
- **驗證方式**：同一輸入下，新路徑與舊路徑輸出相同訂單（暫時保留舊方法做 A/B 比對，S5 完成後刪除）。
- **相依**：S3。

### S5. 改寫三支既有策略 ⬜

- **目的**：把現有策略搬到新的分層鉤子上。
- **做法**：逐支把 `check_*_signal()` 的前半段（篩選）改成 `generate_*_signals()` 回傳 `List[Signal]`，後半段（`return self.calculate_position_size(...)`）刪除——那段由基底接手。
  - `MomentumStrategy1`：參考價 `quote.close`。
  - `ForeignSellShortDayTradeStrategy`：參考價 `quote.open`（放空價）。**這支同時受實盤文件 Phase4-1 影響**（盤前拿不到 `open`），兩份文件都會動到它，**先做本文件、後做 Phase4-1**，否則同一個方法要改兩次。
  - `MomentumFuturesStrategy`：走 `FuturesPortfolioConstructor`。
  - **交易邏輯一行都不改**：篩選條件、門檻常數、參考價選擇、取整規則全部原樣搬移。
- **產出**：三支策略檔。
- **驗證方式**：**`./scripts/run_regression.sh` 零變動，baseline 不重產**。這是整份文件的核心驗收——任何一筆交易變動都代表搬移過程改到了邏輯。
- **相依**：S4。
- **注意**：建議單獨一個 commit，方便回退。

### S6. 與實盤規劃的邊界對齊 ⬜

- **目的**：本文件與[實盤下單架構規劃.md](實盤下單架構規劃.md)會動到相鄰的層，落點要一次講清楚，不要兩份文件各寫一套。
- **做法**：
  - **`max_holdings` 去重**：目前 `EqualWeightSizer.size()` 與 `Backtester.check_max_holdings()` 各檢查一次。
    **落點刻意不預先定案，第一件事是比對兩處語意是否等價。** 兩個候選各有道理：
    - `core/portfolio/`：`sizer` 本來就吃 `max_holdings`，且依本文件〈命名原則〉的判準，
      「最多持有幾檔」回答的是「持有什麼」，屬 portfolio 層。
    - `core/execution/order_preprocess.py`：實盤文件 Phase3-4 的現行規劃，與方向白名單、排序同批處理。

    **但兩者不一定等價**：`sizer` 在訊號階段以候選數截斷，`Backtester.check_max_holdings()` 在逐單階段
    檢查（可能含同一根 bar 稍早已開的倉）。**先寫清楚差異，確認等價才合併；不等價就兩處都留，
    各自寫明職責。** 這一項會動到引擎行為，無論怎麼定案都必須跑回歸雙線確認零變動。
  - **跨策略仲裁的落點已定案為 `core/portfolio/aggregation.py`**（2026-09-19）：判準是該層回答什麼問題——資金分配與同標的仲裁回答「帳戶最終持有什麼」，屬 portfolio 層；`core/execution/` 只保留「委託怎麼送」（方向白名單、排序）。實盤文件的 Phase3-8、Phase3-9 已同步改寫，原先規劃的 `core/execution/portfolio_arbitration.py` 不再使用。
  - 業界通稱是 **portfolio aggregation**：把多個 **sleeve**（帳戶內由單一策略管理的子組合）的部位合成帳戶層。這個詞同時蓋住資金分配與同標的仲裁兩半，比 `allocation`（只有資金）或 `netting`（只有沖銷）都完整。
  - 更新實盤文件 Phase0-4 的分層登記，加入 `core.portfolio`。
- **產出**：[實盤下單架構規劃.md](實盤下單架構規劃.md) 的 Phase0-4、Phase3-4、Phase3-8、Phase3-9（本步驟只對齊文件敘述）。**`core/portfolio/aggregation.py` 的實作不屬於本文件**——它由實盤文件的 Phase3-8、Phase3-9 產出，本文件只負責確立它的落點與所屬分層。
- **驗證方式**：兩份文件的檔案路徑敘述一致，無衝突；`check_layer_deps.py` 通過。
- **相依**：S5。

## 與實盤下單的施作順序

```
S1 → S2 → S3 → S4 → S5（回歸零變動）→ S6 → S7
                          │
                          └─ 之後才做 實盤下單架構規劃.md 的 Phase3-4、Phase4-1
```

**本文件必須排在實盤的 Phase3-4 與 Phase4-1 之前。** 理由：

- Phase4-1 會往 `BaseStrategy` 加 `live_ready`／`live_schedule`／`live_tag`，並要求每支策略補〈實盤執行〉docstring。
- Phase3-4 會動 `Backtester`，是實盤文件裡唯一要跑回歸的步驟。
- `ForeignSellShortDayTradeStrategy` 兩份文件都會改到。

先做實盤再分層的話，同一批檔案要重構兩次、回歸雙線要跑兩次，而且**兩次都動策略層的回歸，出問題時分不出是哪一次造成的**。
