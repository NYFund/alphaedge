# 重構後全專案健檢

## Abstract

- **背景／問題**：2026-09-24 完成 39 步的「架構重構與冗餘收斂」之後，對 `core/`、`tasks/`、
  `scripts/`、`strategy_lab/`、`frontend/`、`tests/`、`docs/` 與工具鏈做了一次全面掃描
  （2026-09-25）。結論是**重構本身收得很乾淨**——零孤兒模組、零無法到達的程式碼、零裸
  `except`、零未使用 import、零 TODO／FIXME 積欠。真正的問題是四類看不見的東西：

  1. **有定義、無執行端**：設定欄位、檢查方法與 parity 類別已經寫好也被文件寫進保證，
     但沒有任何呼叫端。讀文件或讀設定的人會以為某道防線存在。
  2. **假綠燈**：測試與護欄跑得過，但驗不到它宣稱要驗的東西。
  3. **重複實作已經分岔**：同一條規則寫在多處，而其中幾處的語意已經不同。
  4. **照著文件做會出錯**：README、`docs/` 與 `strategy_lab/` 有跑不動的範例、
     不存在的檔案、錯的圖檔名與欄名，而 `check_doc_paths.py` 當時只驗檔案路徑。

- **目標**：把「保證了但不存在的行為」補上或拿掉，讓假綠燈真的會紅，把已分岔的重複
  收斂成一份，並清掉確認零呼叫的殘骸。完成後，文件與設定所描述的每一道防線都真的在跑。

- **範圍界線**：**不做**
  1. 不改任何交易邏輯或成本口徑的**數值**——本份只收斂實作位置與補上缺的執行端，
     凡是會改變回測結果的一律另立步驟並標明須重產 baseline。
  2. 不動 tick 相關程式的結構：`core/pipeline/tw/**tick**`、`core/api/tw/stock_tick_api.py`
     的去留屬 [台股tick改用TimescaleDB.md](台股tick改用TimescaleDB.md)。
  3. 不做 `core/api/` 的公開介面調整——`scripts/check_api_orphan_methods.py` 的判準已明訂
     「`core/` 內部零呼叫」對該層屬正常。
  4. 不重寫測試框架，只修個別測試的斷言方式。
  5. 覆蓋率提升不列入：money path 實測 80–100%，低覆蓋集中在 tick 鏈，屬第 2 點。

- **驗收標準**：
  1. Phase1 的「有定義、無執行端」各自收尾：接上執行端，或移除並改掉宣稱它存在的文件。
  2. Phase2 的每一條假綠燈，都能以「刻意破壞被測行為」驗證它確實會紅。
  3. Phase3 的每組重複，收斂成一份，或兩邊 docstring 互指並寫明差異（比照
     `order_rules.exceeds_symbol_exposure()` 的既有做法；該函式 2026-10-07 前位於 `core/execution/order_preprocess.py`）。
  4. Phase8 的每個範例都實際執行過一次；每個檔名與欄名都與實際產出對得上。
  5. 每一步都通過 `pytest -m "not slow"`、`./scripts/run_regression.sh` 與三支閘門腳本。

- **現況（2026-10-10）**：**45 / 51 完成**。5 步（Phase1-1、Phase1-5、Phase2-8、Phase3-2、Phase3-7）
  已在 `feature/post-rehearsal` 分支實作並驗證，**尚未 merge 進 main**，等
  `實盤下單架構規劃.md` Phase7-1（模擬環境端到端演練）結束後部署；Phase7-1（拆 `core/live/trader.py`）未開始，
  最早 2026-10-20 換月實跑通過、且上述分支 merge 之後才動。已完成步驟的詳細經過留在 git 歷史，
  本文件只保留結論、決策理由與已知限制。
