# 重構後全專案健檢

## Abstract

- **背景／問題**：2026-09-24 完成 39 步的「架構重構與冗餘收斂」之後，對 `core/`、`tasks/`、
  `scripts/`、`strategy_lab/`、`frontend/`、`tests/`、`docs/` 與工具鏈做了一次全面掃描
  （2026-09-25）。結論是**重構本身收得很乾淨**——零孤兒模組、零無法到達的程式碼、零裸
  `except`、零未使用 import、零 TODO／FIXME 積欠，`core/` 型別註解只缺 4 處實質欄位。
  真正的問題不是「搬家留下的死碼」，而是三類看不見的東西：

  1. **有定義、無執行端**：設定欄位、檢查方法與 parity 類別已經寫好也被文件寫進保證，
     但沒有任何呼叫端。讀文件或讀設定的人會以為某道防線存在。
  2. **假綠燈**：測試與護欄跑得過，但驗不到它宣稱要驗的東西——包含一條**自己設定再自己
     斷言**的測試，和一條**指令失敗就無條件通過**的 ratchet。
  3. **重複實作已經分岔**：同一條規則寫在多處，而其中幾處的語意已經不同。

- **目標**：把「保證了但不存在的行為」補上或拿掉，讓假綠燈真的會紅，把已分岔的重複
  收斂成一份，並清掉確認零呼叫的殘骸。完成後，文件與設定所描述的每一道防線都真的在跑。

- **範圍界線**：**不做**
  1. 不改任何交易邏輯或成本口徑的**數值**——本份只收斂實作位置與補上缺的執行端，
     凡是會改變回測結果的一律另立步驟並標明須重產 baseline。
  2. 不動 tick 相關程式的結構：`core/pipeline/tw/**tick**`、`core/api/tw/stock_tick_api.py`
     的去留屬 [台股tick改用TimescaleDB.md](台股tick改用TimescaleDB.md)，本份只改其中
     與該計畫無關的敘述錯誤。
  3. 不做 `core/api/` 的公開介面調整——`scripts/check_api_orphan_methods.py` 的判準已明訂
     「`core/` 內部零呼叫」對該層屬正常。
  4. 不重寫測試框架，只修個別測試的斷言方式。
  5. 覆蓋率提升不列入：money path（`core/live`、`core/broker`、`core/dao`、`core/execution`、
     `core/portfolio`）實測 80–100%，沒有缺口；低覆蓋集中在 tick 鏈，屬第 2 點。

- **驗收標準**：
  1. Phase1 的四項「有定義、無執行端」各自二擇一收尾：接上執行端，或移除並改掉宣稱它存在的文件。
  2. Phase2 的每一條假綠燈，都能以「刻意破壞被測行為」驗證它確實會紅。
  3. Phase3 的每組重複，收斂成一份，或兩邊 docstring 互指並寫明差異（比照
     `order_preprocess.exceeds_symbol_exposure()` 的既有做法）。
  4. 每一步都通過 `pytest -m "not slow"`、`./scripts/run_regression.sh` 與三支閘門腳本。
  5. Phase3-1、Phase3-5 若改變任何成本數字，回歸雙線須重產 baseline 並逐筆比對。

## Phase1：有定義、無執行端

這一組的共同特徵是**設定或文件保證了一道不存在的防線**。比純粹的死碼危險：死碼只是沒人用，
這一類會讓人以為問題已經被擋住。

### Phase1-1. 帳戶總曝險上限接上執行端或移除 ⬜

- **目的**：`RiskConfig` 的 11 個欄位中，只有 `account_exposure_ratio` 沒有任何執行端。
  其餘 10 個都在 `RiskManager` 被消費。它唯一被讀到的地方是 `validate()` 以
  `fields(self)` ＋ `getattr` 做上限驗證——**只驗數值合法，不擋任何單**。
  註解寫著「帳戶總曝險上限」，但帳戶層的曝險檢查根本不存在（帳戶層只有單日虧損一道）。

  這比 `ShortConstraint.allow_below_reference` 更危險：後者有
  `StockCostModel.check_unimplemented_constraints()` 在建構時發警告，這一個**什麼警告都沒有**。
  設成 0.5 會讓人以為帳戶曝險被限在五成。

- **做法**：二擇一。
  1. 在 `RiskManager` 接上帳戶層曝險檢查（比照既有的單一標的曝險截斷）；或
  2. 暫不實作，則比照 `ShortConstraint` 加建構時警告，並在欄位註解寫明「尚未實作」。

- **產出**：`core/live/risk/risk_config.py`、`core/live/risk/risk_manager.py`、對應測試。

- **驗證方式**：走路徑 1 時，設了比例會真的擋單並計數；走路徑 2 時，建構 `RiskConfig`
  會發出警告，且有測試釘住這個狀態（比照 `tests/backtest/test_unimplemented_constraints.py`）。

- **相依**：無。路徑 1 會改變實盤行為，**不可排在演練期間**。

### Phase1-2. 保證金鏈式比對接進 updater 或刪除 ⬜

- **目的**：`FuturesMarginUpdater.check_margin_chain()` 是 60 行的完整實作，docstring 詳述它是
  偵測「TAIFEX 2026/04/21 改措辭導致靜默漏抓」的唯一手段——而它**零呼叫**。
  同時 `docs/futures/tw-futures-platform.md` 寫著「鏈式比對只記缺口、不拒收
  （`check_margin_chain()`）」，把它當成現行機制描述。

  現況是最糟的組合：文件保證了一道防線，而那道防線從來沒有執行過。

- **做法**：二擇一。
  1. 接進 `FuturesMarginUpdater.update()` 的收尾，缺口以 warning 記錄（照 docstring 的「只記不拒」）；或
  2. 刪除方法，並把 docs 那一行改寫成「尚未實作」。

  建議走路徑 1——方法已經寫好，接上的成本遠低於重寫。

- **產出**：`core/pipeline/tw/updaters/futures_margin_updater.py`、
  `docs/futures/tw-futures-platform.md`、對應測試。

- **驗證方式**：人工塞一筆「調整前 ≠ 前一則調整後」的公告，log 出現缺口紀錄且流程不中止。

- **相依**：無。

### Phase1-3. parity 補上 `UNFILLED`／`TIMING` 判定 ⬜

- **目的**：`parity_checker.py` 定義了七個 `CATEGORY_*` 常數，其中 `CATEGORY_UNFILLED`
  與 `CATEGORY_TIMING` **零使用**，`RISK_EVENT_TO_CATEGORY` 也沒映射到它們。
  上方註解寫著「順序即判定優先級」，但這兩個優先級永遠不會命中。

  後果具體：**未成交與時點差都會落進 `UNEXPLAINED`**，而
  [實盤下單架構規劃.md](實盤下單架構規劃.md) Phase7-1 的驗收標準正是「`UNEXPLAINED = 0`」。
  演練期間真的出現一筆未成交，就會讓那條驗收失敗——而它本該被歸類。

- **做法**：補上兩條判定。未成交：實盤有委託但無成交、回測有成交；
  時點差：兩邊都有但段落或時間戳不同。位置在既有的優先級序列中，順序要讓它們排在
  `UNEXPLAINED` 之前。

- **產出**：`core/live/report/parity_checker.py`、`tests/live/test_parity_checker.py`。

- **驗證方式**：造一筆未成交與一筆時點差的比對輸入，各自歸到對應類別而不是 `UNEXPLAINED`。

- **相依**：無。**建議排在 Phase7-1 演練續跑之前**，否則演練的 `UNEXPLAINED` 統計會失真。

### Phase1-4. 公司行動人工補登路徑接出來或刪除 ⬜

- **目的**：`CorporateActionUpdater.load_detected_events()` 零呼叫，而
  `corporate_action_detector.py` 的註解寫著「明確加入（見
  `CorporateActionUpdater.load_detected_events()`）」。ETF 分割（0050 的 2025-06-18 一拆四）
  的人工補登路徑事實上是斷的——偵測得出來，但沒有入口把它寫進去。

- **做法**：二擇一。
  1. 加一支 `scripts/manual/` 入口把它接出來（比照既有 manual 腳本的唯讀與確認慣例）；或
  2. 刪除方法，並改掉 `corporate_action_detector.py` 那句指路。

- **產出**：`scripts/manual/`（新增）或 `core/pipeline/tw/updaters/corporate_action_updater.py`、
  `core/pipeline/tw/cleaners/corporate_action_detector.py`、`scripts/manual/README.md`。

- **驗證方式**：走路徑 1 時，以 0050 的 2025-06-18 分割實跑一次，事件進表且冪等。

- **相依**：無。

## Phase2：假綠燈與護欄缺口

這一組的共同特徵是**測試或護欄看起來在守，實際上驗不到**。每一步的驗證方式都一樣：
刻意破壞被測的行為，那條測試必須紅。

### Phase2-1. 修掉同義反覆的斷言 ⬜

- **目的**：`tests/live/test_account_equity_basis.py` 有一段：

  ```python
  allocator: CapitalAllocator = CapitalAllocator.__new__(CapitalAllocator)
  allocator.safety_ratio = 0.95
  assert allocator.safety_ratio < 1.0
  ```

  **測試自己設定它接著要斷言的值**。docstring 宣稱要釘住「安全係數必然小於 1」，
  但正式常數 `CAPITAL_SAFETY_RATIO` 從頭到尾沒被讀到。有人把它改成 `1.0`，這條照樣綠
  ——而那意味著資金額度檢查的安全邊際消失。

- **做法**：改成從真正建構的 `CapitalAllocator` 實例讀 `safety_ratio`，
  讓正式常數進入斷言路徑。

- **產出**：`tests/live/test_account_equity_basis.py`。

- **驗證方式**：把 `CAPITAL_SAFETY_RATIO` 暫時改成 `1.0`，該條必須紅。

- **相依**：無。

### Phase2-2. ratchet 指令失敗時要紅 ⬜

- **目的**：`tests/test_quality_ratchet.py` 的 `actual_counts()` 跑
  `subprocess.run(["uv","run","ruff",...])` 但**從不檢查 `returncode`**。
  2026-09-25 實測：指令失敗時 `returncode=2`、stdout 為空，於是
  `dict.fromkeys(rules, 0)` 的 0 全部留著，主斷言的 `0 > N` 恆為 False，
  **測試無條件通過**。而那是整份 ratchet 的主測試。

  所幸方向相反的 `test_annotations_are_not_wildly_stale` 會紅，所以兩條成對時是
  fail-safe 的——但那是巧合，不是設計。

- **做法**：`actual_counts()` 加 `assert result.returncode in (0, 1), result.stderr`
  （ruff 有違規時回 1，屬正常）。順帶把兩條測試各自呼叫一次改成共用一次結果——
  現在等於全庫跑兩次 ruff。

- **產出**：`tests/test_quality_ratchet.py`。

- **驗證方式**：把指令換成不存在的規則名讓它失敗，測試必須紅。

- **相依**：無。Phase5-2 相依本步驟（要先有可信的檢查，才能清 ignore 清單）。

### Phase2-3. `exc_info` 護欄擴及 `scripts/` 與 `strategy_lab/` ⬜

- **目的**：`no-stdlib-exc-info` 這條 hook 擋的是「loguru 收到 `exc_info=` 會靜默丟掉
  traceback」。它的 `files` 是 `^(core|tasks)/.*\.py$`，而 CI 端的等價護欄
  `tests/test_entrypoint_and_logging.py` 的掃描範圍寫死 `("core", "tasks")`
  ——**兩道防線範圍一模一樣，同時漏掉同一塊**。

  `scripts/` 有 11 支用 loguru，包含存活監控 `live_watchdog.py`。那支的 docstring 自己寫著
  「監控自己死掉而沒人知道，和沒有監控是同一件事」——而它正是最可能寫
  `logger.error(..., exc_info=True)` 的那種收尾程式碼。目前全庫還沒有人踩到。

- **做法**：兩處同步擴成 `core｜tasks｜scripts｜strategy_lab` 加 `run.py`。
  **兩邊必須一起改**，否則會變成一邊綠一邊紅。

- **產出**：`.pre-commit-config.yaml`、`tests/test_entrypoint_and_logging.py`。

- **驗證方式**：在 `scripts/live_watchdog.py` 塞一個 `exc_info=True`，
  pre-commit 與 pytest 都要紅。

- **相依**：無。

### Phase2-4. per-file-ignores 要驗「規則是否仍觸發」 ⬜

- **目的**：`pyproject.toml` 自己寫著「修掉之後要把對應那條從本清單移除，不要讓它長期留著
  ——留著等於對那類問題永久失明」。但現有的
  `tests/test_config_consistency.py::test_per_file_ignores_point_to_existing_paths()`
  **只檢查路徑存在、不檢查規則是否還會觸發**，所以豁免失效完全沒有訊號。
  實測已經有兩條失效（見 Phase5-2）。

- **做法**：新增一條測試——暫時清空 per-file-ignores 後實跑 ruff，
  比對每條豁免是否仍有對應違規；沒有的就報出來要求移除。

- **產出**：`tests/test_config_consistency.py`。

- **驗證方式**：加一條明顯已失效的豁免，測試必須紅。

- **相依**：無。Phase5-2 相依本步驟。

### Phase2-5. 子行程測試沙箱化 ⬜

- **目的**：`tests/test_run_entry.py` 的 `run_entry()` 以子行程跑 `run.py`，
  但**沒有傳 `env`**——直接繼承 `os.environ`，包含本機 `.env` 的真實金鑰與真實資料根。
  而 `LiveTradeDAO.DEFAULT_DB_PATH` 的 patch 只在行程內有效，子行程會從
  `ALPHAEDGE_DATA_DIR` 重算。

  目前無害（那 13 個 case 全在 argparse 層就 exit 2，碰不到 DB），但這正是根目錄
  `conftest.py` 說明字串記載的那起事故的形狀——一條測試以子行程跑實盤入口、
  用本機金鑰登入模擬環境、累積出 19 筆 `REDUCE_ONLY`。

  安全寫法就在隔壁：`tests/live/test_live_factory_and_entry.py` 的 `_run_cli()`
  沙箱化四個路徑環境變數，並把金鑰清成**空字串而非刪除**
  （`load_dotenv()` 不覆寫已存在的鍵，刪掉反而會被 `.env` 補回來）。

- **做法**：把 `_run_cli()` 的 env 沙箱直接沿用到 `run_entry()`。

- **產出**：`tests/test_run_entry.py`。

- **驗證方式**：13 個 case 行為不變；以不存在的資料根執行仍得到相同退出碼。

- **相依**：無。

### Phase2-6. 補上「掃描結果不得為空」的自驗 ⬜

- **目的**：兩處護欄在結構上會悄悄失效。

  1. `tests/live/test_live_datafeed.py` 從 `inspect.getsource()` 刮出
     `self.x = XxxAPI(` 這種行組成集合，再斷言 `backtest_apis <= live_apis`。
     `TwStockDataFeed.setup` 哪天改用迴圈、dict 或 factory 建 API，
     `backtest_apis` 就變 `set()`，而 **`set() <= 任何東西` 永遠成立**。
  2. `tests/test_symbol_exposure_parity.py` 以字面字串 `"init_capital * max_ratio"`
     當護欄，斷言 `== {}`。有人寫成沒有空格、換行、或把變數改名，
     護欄就再也抓不到東西——而抓不到就是通過。

  專案已經有這個模式的模範：`tests/test_strategy_data_access.py` 先
  `assert len(strategy_source_files()) >= 6` 確認掃描範圍非空，再以**合成的違規程式碼**
  驗證 regex 真的抓得到東西。

- **做法**：兩處都補上「掃描結果非空」的前置斷言；第 2 處另改用 AST 比對，
  並加一段合成違規碼驗證樣式確實命中。

- **產出**：`tests/live/test_live_datafeed.py`、`tests/test_symbol_exposure_parity.py`。

- **驗證方式**：把被掃的程式改寫成迴圈形式（行為不變），兩條測試都必須紅。

- **相依**：無。

### Phase2-7. 脆弱的原始碼字面斷言改為行為斷言 ⬜

- **目的**：數處測試斷言的是實作細節而非行為，無害重構就會紅。這與 Phase2-6 不同：
  那些是「失效而不自知」，這些是「誤報」。兩種都會侵蝕對測試的信任。

  - `tests/test_compose_live_service.py` 整檔六條在比對 YAML 的字面文字
    （`'entrypoint: ["python", "run.py", "--mode", "live"]'` 等），
    而且 `lines.index("  live:")` 縮排一變就是 `ValueError`。
    它正好也是 [回測與實盤入口拆分及架構收斂.md](回測與實盤入口拆分及架構收斂.md)
    Phase1-6 要改 entrypoint 時第一個炸的地方。
  - `tests/live/test_account_equity_basis.py` 斷言 `inspect.getsource()` 含
    `"equity_unavailable()"`、`"verify_quota"` 等方法名，以及
    `source.count("self._account_equity()") >= 3`（釘住呼叫點數量）。
  - `tests/test_entrypoint_and_logging.py` 讀原始碼驗 argparse 旗標，
    但同檔已經在用 subprocess。

- **做法**：compose 那檔改用 `yaml.safe_load()` 比語意；
  `test_account_equity_basis` 改成驗行為（查不到帳務時 `verify_quota` 確實被略過），
  並刪掉 `count >= 3`（保留同檔那條「公式不得被抄第二份」的負向護欄，那是合理的）；
  argparse 那條改跑 `--help` 或檢查 parser 的 `_actions`。

- **產出**：`tests/test_compose_live_service.py`、`tests/live/test_account_equity_basis.py`、
  `tests/test_entrypoint_and_logging.py`。

- **驗證方式**：把 compose 的 list 改成 block style（語意不變），測試要維持綠。

- **相依**：無。**建議排在入口拆分 Phase1-6 之前**，否則那一步會被這檔擋住。

## Phase3：重複實作已漂移或無書面理由

專案對「刻意的重複」有明確慣例：兩邊 docstring 互指並寫明理由
（例如 `core/adapters/__init__.py` 的「這個重複是設計，不是意外，不要合併」，
以及 `order_preprocess.exceeds_symbol_exposure()` 的四面向差異對照表）。
本階段處理的是**沒有寫明理由、或寫了理由但實際已經分岔**的那些。

### Phase3-1. 證交稅公式收斂成一份 ⬜

- **目的**：同一條證交稅規則有兩份實作：

  | 位置 | 當沖減半的判定 |
  |---|---|
  | `StockUtils.calculate_transaction_tax()` | `is_day_trade` 為真就**無條件**套減半 |
  | `StockCostModel.calculate_tax()` | 另外卡 `is_day_trade_tax_effective(date)`（2017-04-28 起） |

  **這是潛伏風險，不是現行錯誤**：2026-09-25 實查，全庫唯一傳 `is_day_trade=True` 的
  地方是 `tests/backtest/test_cost_model.py`，沒有任何生產路徑走那個分支。
  但只要有人從生產程式碼傳了它，2017-04-28 之前的稅就會少算一半，而且不會有任何訊號。

- **做法**：讓 `StockCostModel` 真的委派 `StockUtils`（把日期閘門下推），
  或反過來讓 `StockUtils` 收日期參數。**不可兩邊各留一份公式**。

- **產出**：`core/utils/instrument.py`、`core/backtest/models/cost_model.py`、對應測試。

- **驗證方式**：回歸雙線零變動（目前沒有呼叫端走當沖分支，故不應有任何數字變動）；
  新增一條測試釘住 2017-04-28 前後的稅率差異。

- **相依**：無。與 Phase6-3 同一支檔案，建議同批施作。

### Phase3-2. 日／夜盤時段規則收斂 ⬜

- **目的**：期貨日／夜盤的時段判定寫了四份：

  | 位置 | 寫法 |
  |---|---|
  | `core/market/tw/futures_calendar.py` | `NIGHT_SESSION_OPEN = time(15,0)` / `NIGHT_SESSION_CLOSE = time(5,0)` |
  | `core/broker/tw/shioaji_quote_stream.py` | `if hour >= 15 or hour < 5:` ← **寫死** |
  | `core/live/datafeed/tw/futures_live_datafeed.py` | `hour >= 15 or hour < 5` ← **寫死** |
  | `core/live/intraday/session_guard.py` | `NIGHT_SESSION_START_HOUR = 15` / `..._END_HOUR = 5` |

  四份都有近乎逐字的中文說明，但**沒有任何一份說明為什麼要有第二、三、四份**。
  而且語意已經分岔：第一份對 13:45–15:00 的空檔回 `None`，其餘三份強制歸 DAY。

- **做法**：收斂成一份判定（建議放 `core/market/tw/futures_calendar.py`，
  它已經是市場結構的權威來源），其餘三處改為引用。若因分層不可直接 import，
  至少讓三份都引用同一組常數，並把空檔歸屬明確寫進各自註解。

- **產出**：上列四個檔案、對應測試。

- **驗證方式**：13:45–15:00 與跨午夜兩個邊界，四處判定結果一致；回歸雙線零變動。

- **相依**：無。**會動到實盤判定，不可排在演練期間**。

### Phase3-3. 契約代號拆解收斂成一份 ⬜

- **目的**：`futures_live_datafeed.split_contract_id()` 與
  `shioaji_account_query.split_contract_code()` **逐位元組相同**，只是換了名字。
  而前者的 docstring 正好寫著：

  > **放模組層而不是掛在資料源上**：帳戶重建也要用同一條規則
  > （`live_position_lot` 只記 symbol），各寫一份會在換月時分岔。

  第二份就長在它警告的那條「帳戶重建」路徑上。

- **做法**：`shioaji_account_query` 改呼叫 `split_contract_id()`，刪掉自己那份。
  若分層不允許（`core.broker` 與 `core.live` 的層級），則把函式下推到兩者都可 import 的位置。

- **產出**：`core/broker/tw/shioaji_account_query.py`（或函式的新落點）、對應測試。

- **驗證方式**：期貨換月與帳戶重建的測試全綠；分層檢查 0 違規。

- **相依**：無。

### Phase3-4. `resolve_multiplier` 兩份互指或收斂 ⬜

- **目的**：兩處同名同概念但行為不同：

  | 位置 | 查不到商品時 |
  |---|---|
  | `core/adapters/tw/futures_quote_adapter.py` | 直接 `KeyError`（docstring 明寫是刻意的）|
  | `core/broker/tw/shioaji_quote_stream.py` | 退而取 contract 的 `multiplier`／`unit`，再不行 warning 後回 `0` |

  股票期貨在回測會炸掉、在實盤會靜默回 0（而乘數 0 會讓 PnL 全部算成 0）。
  `core/adapters/__init__.py` 明文列舉「兩邊共用的只有兩樣」（輸出契約與 `quote_validation.py`），
  **乘數解析不在其中，兩份也互不交叉引用**。

- **做法**：兩邊 docstring 互指並寫明 fallback 政策的差異與理由
  （比照 `exceeds_symbol_exposure()` 的四面向對照表）；
  或收斂成一份、由呼叫端決定 fallback 策略。

- **產出**：上列兩個檔案。

- **驗證方式**：兩份 docstring 互相指得到；未登錄商品在兩條路徑的行為各有測試釘住。

- **相依**：無。

### Phase3-5. `strategy_lab` 同檔兩套成本口徑統一 ⬜

- **目的**：`strategy_lab/strategies/tsmc_overnight_signal/pipeline.py` 同時存在兩套成本：
  它已經 `from core.utils.instrument import StockUtils` 並在數處使用，
  但另有 `FEE_BUY` 與 `FEE_SELL_PLUS_TAX` 兩個寫死常數，而寫死版**漏掉了
  `Commission.Discount` 與 `MinFee`**。同一支 pipeline 裡兩處成本互相不一致。

- **做法**：刪掉兩個寫死常數，全部改走 `StockUtils`。

- **產出**：`strategy_lab/strategies/tsmc_overnight_signal/pipeline.py`。

- **驗證方式**：該研究的成本數字重算，**差異要記錄下來**——這一步會改變研究結論的數值，
  不是零變動的重構。

- **相依**：無。屬 `strategy_lab/`，不影響回測與實盤。

### Phase3-6. DAO 與 loader 的結構性重複上提 ⬜

- **目的**：數處逐字相同的實作，且部分已經漂移：

  - `stock_dividend_loader.py` 與 `corporate_action_loader.py` 約 95% 相同，
    `upsert()` 逐字相同，**但只有後者有 `if df.empty: return 0` 守衛**。
  - `create_table()`／`ensure_table()` 在 `monthly_revenue_dao.py` 與
    `financial_statement_dao.py` 逐字相同。
  - `get_by_stock` 在三支 DAO 逐字相同；`get_range`／`get_by_date`／`ensure_table` 各 5 份。
  - `plan_dates()` 在 `stock_chip_updater.py` 與 `stock_margin_updater.py` 逐位元組相同。

  `core/dao/base.py` 已經是共用 SQL helper 的家，`BaseDataLoader` 同理。

- **做法**：逐組上提到基底。**先補齊漂移的那一處**（`if df.empty` 守衛）再合併，
  否則會把缺守衛的版本當成共用實作。

- **產出**：`core/dao/base.py`、`core/pipeline/shared/base_loader.py`、
  上列各 DAO 與 loader。

- **驗證方式**：回歸雙線零變動；各 DAO 的既有測試全綠。

- **相依**：無。建議排在 [PostgreSQL遷移計畫.md](PostgreSQL遷移計畫.md) **之前**——
  那份要改寫 DAO 的 SQLite 專屬語法，先收斂重複可以少改好幾份。

## Phase4：死碼清理

以 AST 全庫索引 ＋ 逐條 grep 複驗（含 `tests/`、`docs/`、`backlog/`、`pyproject.toml`）。
已排除動態呼叫（`getattr` 形式的 cleaner／crawler 分派）、pytest hook、
`StrategyLoader` 的動態載入、CLI enum 迭代。

### Phase4-1. 刪除零呼叫的工具方法 ⬜

- **目的**：八支方法全庫零呼叫、零測試（複驗時的額外命中都是自己的 docstring 範例或註解）：

  | 檔案 | 方法 |
  |---|---|
  | `core/utils/log_manager.py` | `remove_default_handler()`、`add_console_handler()`、`get_logger()` |
  | `core/utils/time.py` | `get_time_diff_in_sec()`、`generate_season_range()` |
  | `core/pipeline/utils/data_utils.py` | `remove_redundant_col()`、`pad2()`、`replace_column_name()` |

  `LogManager` 那三支都是**英文 docstring**，與 CLAUDE.md §1／§2.2 的繁中要求不符
  ——那本身就是重構前留下的標記。`generate_season_range` 是 `generate_year_range` 的死兄弟，
  `(年, 期)` 的場景已全數改用 `generate_year_period_range`。
  `pad2` 的 docstring 說「組 URL 時用」，而組 URL 的那段程式已不存在。

- **做法**：直接刪除。刪 `add_console_handler()` 會順帶消掉 `core/` 四筆 `print` 之一。

- **產出**：上列三個檔案、`core/utils/__init__.py`（若有 re-export）。

- **驗證方式**：全庫 grep 為零；`pytest -m "not slow"` 與回歸雙線全綠。

- **相依**：無。

### Phase4-2. 處置零 importer 的 facade re-export ⬜

- **目的**：10 組 `__init__.py` 的 re-export 沒有任何 importer，呼叫端一律走完整路徑。
  其中兩處特別值得處理：

  1. **自相矛盾**：`core/adapters/__init__.py` 白紙黑字寫著「呼叫端一律用完整路徑……
     套件層 re-export 兩個名字，只會讓同一個類別有兩條 import 路徑」，
     而 `core/adapters/tw/__init__.py` 做的正是它禁止的事，且零 importer。
  2. **全庫唯一自稱相容 shim 的東西**：`core/managers/futures/position_manager.py`
     的 `__all__` 含 `FuturesMarginConfig` 並註明「供既有 import 路徑取用」——
     而 14 個 importer **全部只 import `FuturesPositionManager`**，
     需要 `FuturesMarginConfig` 的 10 處一律走 `core.market.tw.futures_margin_config`。
     全庫也沒有 `import *`，所以那個 `__all__` 條目連作用都沒有。

  其餘 8 組見〈附：零 importer 的 facade 清單〉。

- **做法**：逐組二擇一——刪除，或明訂為 public API 並要求呼叫端改用。
  建議統一刪除，與 `core/adapters/__init__.py` 已宣告的規則一致。

- **產出**：10 個 `__init__.py`。

- **驗證方式**：刪除後全庫 import 不變（`pytest` 與三支閘門腳本全綠）；
  `python -c "import core.models, core.utils, core.execution"` 成功。

- **相依**：無。

### Phase4-3. 清理零使用的常數與 Enum 成員 ⬜

- **目的**：分兩類處理。

  **該刪或該接上**：

  | 位置 | 問題 |
  |---|---|
